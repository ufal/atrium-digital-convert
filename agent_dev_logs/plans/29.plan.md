## Context
After the meeting of 30 September, the ÚFAL tools are cut along the pipeline's stages rather than along the tools'
history. This repository holds two unrelated things: the **LLM keyword stage** (its name, its service, most of its
code) and the **born-digital converter** `digital-convert` (its recent releases, its open issues #10 and #28, and what
AMČR asked for in item 11). The meeting gave the keyword stage to a new repository (nlp-enrich#40) and this repository
to the converter (#29).

The issue leaves the functionality open. Three facts narrow it:
1. **The "JSON of per-page blocks" already exists** — it is the record `digital-convert` writes: `pages[]` (with the
   text-layer census and `needs_ocr`), `lines[]` (with boxes, `group_id` blocks and `style.region`), `tables[]`. No new
   format is needed, and a new one would be a second contract beside the frozen one.
2. **In AMČR's architecture, stages do not call each other.** Temporal activities call the services and chain them
   (report §3.1, item 8); each image passes the trust gate on its own (item 7). A converter that calls
   page-classification and ocr-postprocess would hide two stages inside a third.
3. **The converter must stay light and permissive.** Its `provenance.license` is the most-restrictive union of the
   components that ran (`requirements_digital.txt` header), and a light-engine record resolves to MIT. Anything that
   brings torch, models or copyleft into the image changes every born-digital record.

## §A — The design choices, with the recommendation

### A1. Repository strategy
| Option                                                                                                       | For                                                                                                                                                                                                  | Against                                                                                                                                              |
|--------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| **R-A — rename in place** (the issue's wording) · the LLM code leaves with its history for keyword-extractor | ✅ **recommended.** The open issues (#10, #11, #28) and the two latest releases (0.7.0, 0.8.0) are the converter's; GitHub redirects old git and web URLs; closed issues stay where they were written | the release line and the Zenodo/CITATION identity of "llm-enrich" become the converter's; the SSHOMP record for llm-enrich must be re-pointed        |
| R-B — rename this repository to `atrium-keyword-extractor`, extract the converter into a new dbc repository  | keeps the LLM history in place (it is most of the code)                                                                                                                                              | contradicts the issue and nlp-enrich#40 (which name a *new* keyword repository); moves #10, #28 and the converter's releases away from the converter |
| R-C — a new dbc repository; this one stays the LLM research repository, keyword-extractor takes the service  | smallest move for the converter                                                                                                                                                                      | a third LLM home next to keyword-extractor; the duplication #72 removes comes back                                                                   |

**Mechanics of R-A:** keyword-extractor is created from this repository with `git filter-repo` keeping the paths that
leave (§B), so their history travels; only then are they deleted here. #11 (document understanding, deferred) goes with
the LLM engine by GitHub's *Transfer issue* once keyword-extractor exists.

### A2. The service
| Option                                                                                                         | Verdict                                                                                                                                          |
|----------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| **S-1 — one service, `api-digital`, `POST /reformat`** → the record; `render=md` adds the regenerable Markdown | ✅ **recommended.** One stage, one image, one spec. `/reformat` is the meeting's name; #10 W1's `/convert` is dropped before it is published      |
| S-2 — `/reformat` (file → record) and `/render` (any record → Markdown)                                        | the renderer is useful to keyword-extractor, but as an HTTP call it would be a service-to-service dependency; it travels as vendored code (§B.3) |
| S-3 — stay a command-line image                                                                                | ❌ AMČR's Temporal activities call services (item 8); #28 exists for this                                                                         |

`/reformat` takes a multipart `file` and an optional `document_json` (the AMČR seed), and returns the record, the
optional Markdown, the `CreateAction` (#71 R2) and, on refusal, the registered reason (`ocr_text_layer` 422;
`unsupported_media_type` 415 with the converter's `cause`). The detailed contract is #28's (#10 §12 W1, W6).

### A3. "Calls to ocr-postprocess and page-classification to describe pages"
| Option                                                                                                                                                                                                                                                                                                                | Verdict                                                                                                                                                                                          |
|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **P-1 — Temporal chains them.** dbc describes what it can measure itself: text-layer census, `needs_ocr` and its reason, page labels, canvas, regions, blocks, tables. page-classification (`/predict_document` on the same PDF) and ocr-postprocess (scoring the born-digital lines, #10 W3) are the next activities | ✅ **recommended.** Each stage stays independently deployable, versioned and gated; the route step already decides the order (report §3.1)                                                        |
| P-2 — bundle the page classifier and the line-quality model in-process                                                                                                                                                                                                                                                | ❌ torch and model weights in the light image; a second copy of two models; the licence union changes for every record                                                                            |
| P-3 — dbc calls the two services over HTTP                                                                                                                                                                                                                                                                            | ❌ in production: retries, timeouts and failure handling outside Temporal; three images behind one trust-gate review. Acceptable only in a developer CLI or a Galaxy demo, never in `api-digital` |

What "describe pages for further processing steps" needs from dbc is therefore **the flags the route step reads**:
`needs_ocr` per page (→ the ATR/OCR service for those pages, #10 W4), and the reason codes that refuse a whole document
(`ocr_text_layer` → re-OCR).

### A4. The "per-page blocks" view
| Option                                                                                                       | Verdict                                                                                        |
|--------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------|
| **V-1 — the record is the output.** Blocks are `lines[]` grouped by `group_id` within `page`                 | ✅ **recommended.** No new contract; the Digital Archive's per-page index reads the same record |
| V-2 — an optional response projection, `view=pages`: `pages[i].blocks[]` built from the record, never stored | only if AMČR asks for it; regenerable, so it belongs beside the Markdown, not in the record    |
| V-3 — a new `blocks` block in the schema                                                                     | ❌ a second, redundant positional plane; re-attribution rules would apply                       |

### A5. The born-digital types
- **PDF, DOCX**: today's light engine.
- **ODT, RTF, XLSX, ODS**: through ocr-postprocess's readers (`text_formats.py`), **vendored with SHA pins**, the
  pattern `tests/test_vendored_teitok_parity.py` already uses for nlp-enrich's TEITOK files — the "one document reader"
  of #72, shared, not forked.
- **DOC, XLS**: LibreOffice headless (`soffice --convert-to docx|xlsx`, MPL-2.0) **inside the `api-digital` image**,
  declared in `para_config.txt` as a conditional component. Alternatives weighed: a separate image only for legacy
  Office (a second service for one conversion) and conversion in the route step (moves ÚFAL's accepted work to AMČR).
  The image grows by a few hundred MB, small beside the 150–200 GB of CUDA images the compute server must hold.
- **Docling** stays a local, opt-in target (`digital-docling`), never in `api-digital` (#10 W7).

this repository vendors nlp-enrich's TEITOK reader. Promoting it to a hub canonical file (para-drift) is the
alternative if a third consumer appears.

## §C — Sequence (the order matters)
1. **Agree the name** (spelling) and the successor map in the record (hub, *`doc-schema-v1` as the pilot baseline*):
   the program `llm-enrich` is succeeded by `keyword-extractor`; `digital-convert` is unchanged.
2. **Last release of the LLM line here** — the pending 0.9.0 (#70's `--detail` profiles) — so keyword-extractor
   starts from a tagged state.
3. **keyword-extractor created** from this repository's history (§B.2 paths) and nlp-enrich's `keywords.py`
   (nlp-enrich#40). Its CI green before anything is deleted here.
4. **Delete §B.2 here** in one commit: code, targets, compose profiles, `para_config.txt` rows, README sections. The
   `api` target and `service/api.py` go; `service/` is rebuilt by #28.
5. **Rename the repository** (GitHub settings). Then, in one window: `SERVICE`, `CITATION.cff` (title, abstract,
   keywords), README (the *"LLM-only sibling"* note becomes a *converter* introduction), `docker.yml`
   `image-name`, compose image names, `security.yml:57` `image-ref` (scans the `-llm` image today; `-api-digital` after), `tests/openapi_contract_data.py`.
6. **Hub, in the same window:** `scripts/revendor_shared.sh:72`, `update_issues.sh` `REPOS`,
   `e2e-digital-smoke.yml:121` (`DIGITAL_IMAGE`), `e2e-pipeline-smoke.yml:426-460` (the LLM step moves to
   keyword-extractor's image), `docs_site/workflows/llm-enrich.md` → `digital-born-convertor.md`, `mkdocs.yml`
   nav, the landing cards. Outside: the ARUP-CAS fork, the SSHOMP records (the llm-enrich record describes the keyword
   stage now; dbc needs its own), the Galaxy wrappers (#66).
7. **#28 `api-digital` does not wait for any of this.** It is built beside the LLM service now (#28 plan §A), with the
   destination's service id (`atrium-digital-born-convertor`) and its own spec asset (`openapi-digital.json`) from its
   first release (a minor 0.x release: it only adds), so steps 3–6 change only the repository's identity, never the service's. The
   first release after step 4 is **1.0.0** (the LLM endpoints are gone).
