## 0 — Operating principle

The project should not choose one *file format* and force every upstream/downstream component to use it. It should choose one **model-facing representation** and keep explicit source-of-truth representations underneath it.

The target architecture is therefore:

- **source/input:** PDF, DOCX and other accepted source formats;
- **canonical pipeline state:** frozen `atrium_document` JSON (`doc-schema-v1`);
- **spatial truth:** PAGE/ALTO/TEITOK-derived line/page geometry, especially for OCR-derived material;
- **LLM view:** one annotated Markdown dialect rendered from the canonical record or TEITOK;
- **LLM application owner:** current `keyword-extract` for the moved LLM/vocabulary stage;
- **benchmark/evaluation:** hub `atrium-project#22` when the AMČR pilot is complete and a gold set exists.

The one-format rule applies to the **LLM view**, not to the archive's source formats.

## 2 — Format contract

### 2.1 Canonical LLM diet: annotated Markdown

The LLM sees Markdown with a controlled set of comments/cues, not arbitrary HTML and not raw XML.

At minimum the rendered view should preserve:

- document/page boundaries and page labels;
- reading order;
- headings/paragraphs/list structure;
- simple and structured tables;
- footnotes and document furniture where available;
- bbox/geometry cues where available;
- OCR/needs-OCR state;
- enough page metadata to recover a grounded citation.

The current implementation already does this through:

- `api_util/json_to_md.py` — canonical record → Markdown;
- `api_util/xml_to_md.py --format layout` — TEITOK/ALTO → same Markdown;
- `api_util/layout_md.py` — shared cue vocabulary and detail profiles.

The old idea of injecting a bare `<!-- Page N -->` marker therefore becomes the much richer **house cue layer**, while page-level citation semantics remain the same requirement.

### 2.2 Source-of-truth hierarchy

```text
original source (PDF/DOCX/etc.)
          │
          ▼
  parser / OCR / NLP stages
          │
          ▼
  atrium_document JSON ────────────────┐
          │                             │
          │                             └── structured metadata / model outputs
          │
          ├──► TEITOK / ALTO truth
          │
          └──► canonical annotated Markdown
                         │
                         ▼
                    model input
```

The model-facing Markdown must be **regenerable from the source record**. It must not become a second mutable datastore.

## 3 — Renderer invariants

### 3.1 One cue dialect

`json_to_md.py` and `xml_to_md.py` must stay on the same `layout_md.py` cue vocabulary. Any new cue must be added once and reused by both paths.

Do not reintroduce the old situation where PDF/DOCX conversion, TEITOK conversion and OCR conversion emit different flavours of Markdown.

### 3.2 Record data only, never prior LLM output

`json_to_md.py` deliberately reads:

- `pages`;
- `lines`;
- `tables`;
- `content`;
- layout/source metadata.

It deliberately **does not read `enrichment`**.

This must be treated as a hard security/correctness invariant for repeated processing: the model must not receive its own previous answer as part of its next input merely because that answer happens to be present in the document record.

### 3.3 Quality filtering is upstream state, not prompt logic

`json_to_md.py` already filters the semantic set of untrustworthy line categories using the hub-canonical vocabulary. This includes the OCR-side `Trash` category after the 2026-09-25 defect fix.

The renderer should continue to **consume** the recorded quality decision, not reproduce the OCR scorer.

### 3.4 Preserve non-numeric and legacy page labels

Page labels may be `iv`, `A-1`, etc. The schema deliberately keeps labels as strings. The renderer uses page indices/order for sorting while preserving the human-visible label for the cue/citation surface.

Do not regress to integer-only page assumptions.

### 3.5 Detail profiles are views, not new formats

The current profiles are:

- `full` — default;
- `standard` — lighter cue set;
- `minimal` — still structured, but with a much smaller cue budget.

All three must produce the **same underlying document text and page sequence**. Only the amount of layout metadata changes.

## 4 — Input routing and parser ownership

### 4.1 `atrium-page-classification`

Treat page classification as a **router for treatment**:

- text-rich/digital-born → deterministic extraction;
- pages needing OCR → OCR connector / OCR postprocess path;
- complex tables or layouts → future layout-aware parser route;
- image/plate-like pages → preserve as non-text/visual content and mark the record accordingly.

Do not create “Markdown path” vs. “HTML+CSS path” at the classifier level. The final LLM view stays annotated Markdown.

The current `/predict_document` PDF service and its record/error contract already provide the right abstraction level; #3 should only specify how its output maps onto the conversion pipeline.

### 4.2 `atrium-ocr-postprocess`

This repository now owns the shared readers and OCR-side scoring/merge logic. `digital-convert` should vendor/reuse those readers with explicit parity checks rather than maintain a second interpretation of ALTO/PAGE/TEITOK inputs.

A born-digital record can carry `lines[].quality_score`, `lines[].categ`, `pages[].needs_ocr`, etc. The renderer consumes those fields but does not recompute them.

The production route for a PDF with an earlier OCR text layer is now explicit: reject it in the born-digital service with the registered `ocr_text_layer` reason (HTTP 422) and hand the document toward the OCR route.

### 4.3 `atrium-nlp-enrich`

`nlp-enrich` remains responsible for the LINDAT text-processing stage and TEITOK format 2. Its former LLM/vocabulary stack is gone.

Its TEITOK output is still a first-class source for the Markdown renderer because it carries page/line structure and spatial annotations. The renderer must therefore continue to support real format-2 TEITOK data, including page breaks within sentences and nontrivial line/block structure.

### 4.4 `atrium-keyword-extract`

This is now the owner of the moved LLM and vocabulary code. The current release has the service boundary in place (`/extract_keywords`) and the statistical kind implemented; controlled LLM extraction is not yet live.

Before the controlled LLM path is enabled, settle the renderer integration explicitly:

1. `keyword-extract` consumes the record after `nlp-enrich`;
2. the LLM receives the canonical annotated Markdown view generated from source-plane data;
3. `enrichment`/keyword results are emitted after inference and are never fed back into `json_to_md` as source content on the next run;
4. there is only one active Markdown cue vocabulary across the ecosystem.

The existing `keyword-extract#1` plan proposes vendoring shared renderer code from the converter with SHA pins. Whether the implementation ultimately uses vendoring or a shared packaged module, the **behavioural contract must remain one dialect** and must be tested against converter fixtures.

### 4.5 `atrium-translator`

Translation can happen downstream of the record and may return a modified `document_json`, but it must preserve the schema contract and must not define a separate “translated LLM input format”.

Any translation-aware LLM workflow must re-render from the current record after translation rather than reusing a stale Markdown snapshot.

## 5 — Benchmark and empirical validation

### 5.1 What is already decided

The generic question “Markdown vs. HTML vs. TXT” is no longer the main experiment. The architecture has already selected annotated Markdown as the default LLM view.

The empirical work now answers narrower questions:

- Does the selected parser preserve the structure we need on difficult inputs?
- Do `full`, `standard` and `minimal` cues preserve model quality while reducing token cost?
- Do page labels/cues survive a full model round-trip well enough for grounded citations?
- Where should complex-layout pages switch from the lightweight born-digital parser to Docling/MinerU or another candidate?

### 5.2 Hub #22 status

`ufal/atrium-project#22` is currently **deferred until after the AMČR pilot** because the in-domain gold set is still missing.

Its existing tooling is still useful:

- `sample_stratify.py` — deterministic quality-tier sampling;
- `eval_metrics.py` — CER/WER, normalized edit distance, entity F1, optional TEDS;
- `bench_compare.py` — per-page/per-tier comparison harness.

When #22 resumes, use the same gold set to compare the detail profiles and parser candidates. Do not restart the methodology from scratch.

### 5.3 Token-cost work

The detail-budget experiment has already shown large reductions in emitted layout characters for real scan-derived documents when moving from `full` to `standard` and `minimal`. These numbers are useful as a motivation, but they are **not yet a quality result**.

Therefore:

- keep `full` as the default;
- expose `standard`/`minimal` as deterministic alternatives;
- benchmark quality before changing the production default.

### 5.4 Complex-layout work belongs to #4

The Docling/MinerU evaluation is now explicitly part of the born-digital conversion path (`digital-convert#4` W7), not a generic LLM benchmark item.

The comparison should focus on the real difficult pages that motivated the issue: multi-column reading order, complex tables, unusual page furniture, mathematical notation, and other layouts where deterministic extraction becomes unreliable.

For each candidate, capture:

- page/text fidelity;
- reading-order correctness;
- table preservation;
- page-marker/page-label fidelity;
- cue compatibility with the house Markdown renderer;
- resource/dependency footprint;
- license constraints relevant to the production image.

## 6 — Stress-test the canonical renderers

The old 2026-08-02 task should be re-scoped and kept as a small deterministic suite.

### Fixtures

Create:

1. **one fully accreted `atrium_document` fixture** containing:
   - multiple pages;
   - non-numeric labels;
   - `page_index`;
   - bbox and canvas metadata;
   - headers/footers/footnotes;
   - grouped paragraphs;
   - tables and merged cells;
   - `needs_ocr`/OCR metadata;
   - quality categories and scores;
   - edge-case Unicode.
2. **one TEITOK format-2 fixture** containing:
   - entities;
   - `<dtok>`;
   - `<pb/>` inside a sentence;
   - page/line bboxes;
   - print-space coordinates where applicable;
   - format quirks already represented by the real `CTX000000002` fixture.

### Assertions

The stress suite should assert:

- no unhandled exception;
- every source page survives exactly once;
- page order is stable;
- every source text line survives exactly once unless the line is intentionally filtered by the quality policy;
- all expected page/bbox/layout/OCR cues survive;
- grouped structure and table anchors survive;
- `enrichment` is not consulted;
- repeated rendering is deterministic.

Do **not** assert that keyword/entity/enrichment blocks appear in Markdown. Validate those fields on the record instead.

## 7 — Page citation contract

The first part is already in place: the record/rendering path retains page identity and page labels through the Markdown view.

The remaining work is the **consumer-facing citation contract**. Decide one stable surface such as:

```text
[Source: <doc_id>, Page: <page-label>]
```

or an equivalent machine-readable form, and verify the complete round-trip:

```text
record → annotated MD → LLM answer → page locator → source record
```

The verifier must use the same page labels the renderer emits; it must not reverse-engineer page order from raw token offsets.

This should stay downstream of the format decision. Do not block the converter work on the final wording of the natural-language citation string.

## 8 — FAIR / roadmap layer

The original research suggested a hierarchical `SKILL.md` / `INDEX.md` navigation layer for agentic retrieval. Keep that as a later layer above the document representation.

The order is:

1. prove the document record and Markdown contract;
2. prove parser quality / cue fidelity;
3. prove token/detail trade-offs;
4. then add corpus-level roadmap/index structures.

Do not introduce an additional metadata/index format into the per-document LLM input contract before the document representation itself is stable.

## 9 — Service and release integration

`digital-convert#4` already established the adopted W1–W7 born-digital sequence, and #2 is the production service issue. The format contract should therefore be reflected in service behaviour rather than implemented as a one-off CLI convention.

Required service-level invariants:

- the `/reformat` output record is valid under `doc-schema-v1`;
- PDF/DOCX parsing and JSON rendering use the same code path as the CLI;
- `ocr_text_layer` is a stable published reason code;
- a document routed to OCR is not silently treated as born-digital;
- the service does not expose a second HTML-only or raw-text-only “LLM mode” as a hidden alternative;
- the `regenerable.markdown` recipe, if emitted, identifies the converter/profile deterministically enough for re-rendering.

The converter may keep compatibility flags for deprecated legacy paths, but the production service should use the canonical JSON → Markdown architecture.

## 12 — Done criteria for Issue #3

Issue #3 can be treated as substantively resolved when all of the following are true:

1. **Format contract:** annotated Markdown is explicitly documented as the single general LLM input representation.
2. **Source truth:** PDF/DOCX/TEITOK/PAGE/ALTO remain upstream representations; no model-facing consumer depends on raw HTML or raw XML as its general prompt dialect.
3. **Canonical renderer:** JSON and TEITOK routes emit the same cue vocabulary and compatible page labels/order.
4. **No enrichment replay:** the renderer never uses prior model outputs as source text.
5. **Routing ownership:** page-classification routes treatment; OCR/postprocess owns OCR reading/scoring; digital-convert owns born-digital conversion.
6. **LLM ownership:** keyword-extract consumes the record and uses the canonical model-facing representation; it does not invent a second Markdown dialect.
7. **Service contract:** `/reformat` exposes the same canonical record/rendering behaviour as the CLI, including stable OCR-routing errors.
8. **Benchmark closure:** after the pilot, #22 supplies an in-domain gold set and reports the quality/token/citation trade-offs for detail profiles and complex-layout parser choices.

## 13 — What this issue does *not* decide

- It does not choose an OCR engine for all archival pages.
- It does not choose the final complex-layout parser before the empirical #4/#22 work.
- It does not define the LLM prompt/template for controlled vocabulary extraction.
- It does not move entity/keyword enrichment into Markdown.
- It does not redesign `doc-schema-v1`.
- It does not require a corpus-wide RAG/vector index before the document representation is stable.
