## Context

The original #1/#29 plan assumed that the existing `atrium-llm-enrich` repository would be renamed in place to a born-digital converter. That is no longer the implementation reality: a **new `ufal/atrium-digital-convert` repository already exists**, the ARUP-CAS fork was recreated against it, and `v1.0.0-beta` has already been released from the new repository.

The remaining work is therefore a **content and release migration**, not another GitHub repository move:

1. make the new repository contain only the born-digital stage;
2. move/converge the remaining LLM and vocabulary implementation into the already-created `atrium-keyword-extract` repository;
3. replace the inherited keyword API with the dedicated born-digital `/reformat` API from #2;
4. publish the converter under its final service/image identity;
5. preserve the existing `atrium_document` contract and integrate with the current six-stage pipeline without service-to-service coupling inside the converter.

The architecture rule from #72 is the main constraint: **one production image per stage, one governed owner for shared layers, one maintained copy of each shared implementation, and the production image must contain only the files needed for its stage.**

## Design rules

### 1. No more repository rename work

The agreed repository identity is already `ufal/atrium-digital-convert`. Do not recreate the repository, rename it again, or create an `atrium-digital-born-convertor` successor.

The old `atrium-llm-enrich` repository remains the historical predecessor. Its retirement/archival state is a separate repository-management action under #72; this issue should only ensure that all live references point to the new converter repository.

### 2. The record contract is unchanged

The converter continues to write the current `atrium_document` shape and the program id **`digital-convert`**. The migration must not re-attribute existing converter blocks merely because the repository changed.

For a seeded request, the API must preserve:

* `doc_id`;
* `source.sha512`;
* source filename;
* source media type;
* the correct `source.origin` ownership;
* the positional fields written by the converter (`pages`, `content`, `lines`, `tables`, geometry/style metadata).

The seed contract is defined centrally by [atrium-project#71](https://github.com/ufal/atrium-project/issues/71), not by a second converter-specific schema.

### 3. `/reformat` is the only production API of this repository

The target production endpoint is:

```text
POST /reformat
```

The intended shape is:

```text
file + optional document_json seed
        ↓
   digital-convert
        ↓
  atrium_document record
  + optional Markdown projection
  + CreateAction paradata
```

The repository must not keep `/extract_keywords` or `/extract_keywords_text` as compatibility production endpoints. Those belong to `atrium-keyword-extract`.

The exact public service id should be pinned before the first API release. The current project deployment convention and the latest #2 request point to **`atrium-digital-convert`**, matching the repository and the requested image prefix.

### 4. `/reformat` calls no other processing service; `/describe` may, when configured

The production route is orchestrated outside the converter: Temporal chains the stages, and **`/reformat` makes no HTTP calls** to `page-classification` or `ocr-postprocess` (the 30 September statement to AMČR holds).

Since 2026-10-04 the service has a second, optional endpoint, **`/describe`** (#2), for sandbox, triage and demo use. It converts the document and then calls page-classification and ocr-postprocess **only when their URLs are configured**, so that it can report per page whether the text layer is usable, what kind of page it is, whether the text reads, and the route the page should take. Every record write still goes through the stage's own accretion, and the converter guards what comes back. When a stage is not configured, not running, or answers badly, `/describe` still answers, with the stage's status.

The converter only supplies the signals needed by the route:

* `needs_ocr` / `needs_ocr_reason` for pages that need reprocessing;
* the registered `ocr_text_layer` refusal for documents that are not legitimately born-digital.

### 5. One LLM/vocabulary implementation

`atrium-keyword-extract` already contains the LLM/vocabulary implementation. The copy that remains in `atrium-digital-convert` must leave this tree. Do not leave a second active copy in the converter “for compatibility”.

The migration should preserve file history where practical, but the outcome is more important than mechanically duplicating history: **one maintained implementation, one production owner, no divergence.**

The converter's release line must therefore lose at least the current LLM/vocabulary modules and dependencies, including the inherited keyword API, LLM configs/clients, prompt assets, vocabulary build/manager code and their tests.

### 6. Production image convention

Follow the hub's #72 rule:

* **production API image:** `ghcr.io/ufal/atrium-digital-convert-api`;
* **batch/CLI image:** `ghcr.io/ufal/atrium-digital-convert-digital`.

The service may be described internally as `api-digital` because that is the issue/#2 service name, but its published production image should follow the hub's standard `-api` naming.

The production-image manifest must describe the actual API entrypoint and only the first-party files reachable by that entrypoint. The old keyword/LLM files must disappear from `.github/production-image.json` before the final release.

## Execution strategy

## A. Freeze the destination identity first

1. Keep `ufal/atrium-digital-convert` as the repository name.
2. Pin the production service id to `atrium-digital-convert` in #2 before publishing the API image, unless AMČR records a different value explicitly.
3. Keep `digital-convert` as the record program id.
4. Treat `v1.0.0-beta` as a transitional prerelease, not the final converter contract.
5. The first release after the migration is **`v1.1.0-beta`** (maintainer, 2026-10-04; it replaces the `v1.0.0` agreed on 30 September because `v1.0.0-beta` already exists). A stable `1.x.0` follows once the hub's seeded born-digital E2E is green.

The old `atrium-llm-enrich` identity must not remain in any production-facing service metadata after this step.

## B. Converge the LLM/vocabulary code into `keyword-extract`

The new keyword repository already exists and already contains a working LLM/vocabulary copy. Therefore the task is not “create a keyword repo” but “remove the remaining duplicate from digital-convert and make keyword-extract the only maintained owner”.

The exact final split should be checked against the current `atrium-keyword-extract` tree before deletion, because that repository already contains the corresponding implementation and its own release/CI wiring.

### Migration rule

0. **Measured 2026-10-04:** `llm_config.txt`, `prompt_template.py`, `prompts/`, `vocab_manager.py`, `vocab_review.py`, `vocab_sources.py` and `corpus_review.py` are byte-identical in keyword-extract. `llm_utils.py` (~400 lines) and `vocab_build.py` (43 lines) differ, and `requirements_llm.txt` differs. `llm_client_shared.py`, `openrouter_client.py`, `ollama_client.py`, `requirements_remote.txt` and their tests are **absent** there. Hence step 2 becomes a transfer manifest: keyword-extract#2 takes these files from tag `v1.0.0-beta` / commit `770ab3f`, where their history stays reachable. This repository deletes them now.
1. Compare the two copies and identify any converter-local changes that have not already reached `keyword-extract`.
2. Transfer only the still-needed implementation/history to `keyword-extract`.
3. Verify `keyword-extract` CI and its API tests before removing the duplicate.
4. Remove the duplicate files and dependencies from `digital-convert` in one deliberate migration commit.
5. Verify that no production converter import path can still reach the LLM/keyword code.

Do not move the born-digital converter back into `keyword-extract`; the direction is one-way: **keyword code → keyword-extract, converter code → digital-convert**.

## C. Rebuild the service surface as `api-digital`

Replace the inherited `service/api.py` with a small FastAPI wrapper around the existing converter core.

### Required endpoints

At minimum:

* `GET /info`
* `GET /health`
* `GET /ready`
* `POST /reformat`

Use the shared ATRIUM service helpers already used by translator, nlp-enrich, page-classification and the other current services.

### `POST /reformat`

The request should support:

* the original uploaded file;
* an optional `document_json` seed record;
* an explicit Markdown/render option only when requested.

The response should carry:

* the resulting `document_json` record;
* the optional Markdown projection;
* `paradata` as the run's Process Run Crate `CreateAction`;
* `limits_applied` where applicable, following the common service contract.

Errors must use the common ATRIUM error shape and registered reason codes.

### Seed handling

The API should enforce the #71 seed rules:

* seed `doc_id` survives unchanged;
* seed `source.sha512` survives unchanged;
* filename and media type survive unchanged;
* `source.origin` remains owned by the tool that actually reads the source.

The #2 decision also adds:

* compare `source.sha512` with the uploaded bytes;
* refuse a mismatch with `source_digest_mismatch`.

That implementation should be shared with the central contract tests so the converter does not invent its own error format.

### OCR text-layer contract

Retain the existing registered `ocr_text_layer` refusal. The **mixed-PDF threshold** must be made explicit in #2 before the service contract is frozen; do not silently turn the current implementation threshold into an undocumented permanent API rule.

For pages that are returned in the born-digital record but need OCR, write `needs_ocr` and its registered reason at page level. The converter does not invoke OCR itself.

## D. Finish the born-digital input support from #2

Retain the working PDF/DOCX converter, then add the production inputs in the agreed order:

1. PDF
2. DOCX
3. ODT / RTF / XLSX / ODS through the governed text-bearing reader path
4. DOC / XLS through the agreed LibreOffice conversion path

The important architectural distinction is:

* `digital-convert` keeps the **rich born-digital positional writer** needed for the record;
* `ocr-postprocess` owns the **common document-reading/quality layer** where the shared contract requires it;
* any vendored shared reader code is pinned and parity-checked rather than silently forked.

The converter must remain CPU-oriented. The optional heavy document-understanding target can remain a local/non-production build; it must not leak into the production API image.

## E. Wire the common downstream semantics, not duplicate them

### OCR hand-off

For a born-digital document containing pages that need OCR:

```text
digital-convert
    │
    ├── normal pages stay in the digital record
    │
    └── needs_ocr pages ──> Temporal ──> ocr-postprocess
                                      │
                                      └── merge back into the SAME doc_id
```

The converter must not produce a second document identity for the OCR pages.

### Quality

`ocr-postprocess` remains the owner of the final line-quality categorisation. `digital-convert` may compute local decode/text-layer diagnostics needed to decide `needs_ocr`, but it should not introduce a second production quality model for downstream indexing.

### NLP / TEITOK

`nlp-enrich` consumes the same record. For born-digital inputs without ALTO, the agreed route is to derive TEITOK geometry from the record's native `pages[].canvas` and `lines[].bbox` rather than force the converter to manufacture an ALTO file just for downstream compatibility.

### Keywords

`keyword-extract` runs later. `digital-convert` does not produce or own either statistical or controlled keywords.

## F. Clean the repository identity and metadata in one pass

After the code split, update all first-party metadata that still says `llm-enrich`:

* `README.md` title, description, links and badges;
* `CITATION.cff` title, repository URL and description;
* `para_config.txt` tool identity, repository fallback and component table;
* `service/README.md` for `/reformat`;
* `service/openapi.json` generated from the new API;
* `.github/production-image.json`;
* `Dockerfile` targets/comments;
* `docker-compose.yaml` and GPU/local compose files;
* `security.yml`, image refs and service labels;

* tests that assert `SERVICE`, repository URLs or image names.

The converter's paradata configuration should list only components actually used by its own production path. The LLM/vocabulary component rows leave with the keyword stage; they must not survive merely because the source file was copied historically.

## Release sequence

```text
Current v1.0.0-beta (transitional)
          │
          ├── confirm final API/service identity
          │
          ├── converge LLM/vocab → keyword-extract
          │
          ├── remove inherited keyword service from digital-convert
          │
          ├── build /reformat + seed + paradata contract (#2 / #71)
          │
          ├── add production image ...-api
          │
          ├── clean metadata / Compose / production-image manifest
          │
          ├── refresh hub references + seeded E2E
          │
          └── full six-stage verification
                    │
                    ▼
             v1.1.0-beta   (maintainer's decision, 2026-10-04)
```

**Release-gate precondition.** `v1.0.0-beta` was published as a full release carrying the LLM `openapi.json`. `atrium_openapi.compare` takes the highest non-prerelease below the new tag as its baseline. A `v1.1.0-beta` that drops `/extract_keywords*` keeps major 1, so the removal counts as breaking and the release fails. Marking `v1.0.0-beta` a **pre-release** on GitHub (pre-releases never count as a baseline) makes `v1.1.0-beta` the bootstrap of the digital spec. Check it with release.yml's `workflow_dispatch` dry run before tagging. The spec also declares the rename (`x-atrium-service-previous: atrium-llm-enrich`), so the identity change passes either way.

The important order is to **remove the old ownership before freezing the new identity**. Otherwise the repository can publish a new-looking converter while still carrying a hidden second LLM/keyword implementation and the old API package metadata.
