## Context

#4 started as a document-understanding research question: how to handle PDFs whose visible text is represented by curves, scans or trustworthy digital text, how to accept DOCX, and whether DOCX/HTML should become an intermediate format for an LLM.

That question has now been resolved into a record-first architecture. The converter is the **born-digital originator** for the ATRIUM document model. Its primary job is to produce a valid `atrium_document` record and to expose the page-level decisions needed by the orchestration layer. An annotated Markdown document is a derived, optional representation of that record for document-level consumers.

The production service work is no longer in this issue. It is [digital-convert#2](https://github.com/ufal/atrium-digital-convert/issues/2), where the current design is being implemented as `api-digital` with `POST /reformat`.

The current route is:

```text
AMČR seed / source bytes
        │
        ├── scanned/image-originated branch → page-classification → OCR → ocr-postprocess
        │
        └── born-digital branch → digital-convert
                                  │
                                  ├── `atrium_document` record
                                  │      ├── source / identity
                                  │      ├── pages / canvas
                                  │      ├── lines / bboxes
                                  │      ├── blocks / regions / tables
                                  │      └── `needs_ocr`
                                  │
                                  └── optional annotated Markdown

                    common record
                         │
                         ▼
                  ocr-postprocess
                         │
                         ▼
                    nlp-enrich
                         │
                         ▼
                 keyword-extract
                         │
                         ▼
                    translator
```

The important boundary is orchestration: `POST /reformat` does **not** call the other repositories directly (the optional `POST /describe` does, when `PAGE_CLASSIFICATION_URL` / `OCR_POSTPROCESS_URL` are set). Temporal / the AMČR route decides whether OCR is needed, invokes the OCR connector, and sends the resulting ALTO/page data to `ocr-postprocess` for the merge.

## Design objectives

1. Keep one canonical document representation: `atrium_document`.
2. Preserve source identity and geometry through the born-digital stage.
3. Detect unusable embedded text instead of silently treating every extracted character as trustworthy.
4. Treat curve-only and scanned PDFs as OCR-required material rather than inventing a second internal OCR stack.
5. Allow page-level `needs_ocr` so mixed documents can retain good born-digital pages.
6. Keep the registered `ocr_text_layer` refusal stable for the agreed prior-OCR whole-document policy.
7. Make Markdown a derived renderer, not a second source of truth.
8. Keep the light digital reader permissive and production-friendly; move complex-layout quality into an explicit evaluation phase.
9. Reuse the shared reader/quality/schema contracts instead of rebuilding copies in each repository.
10. Leave the production API/service work to #2 and close #4 only when the adopted design is actually exercised by that implementation.

## §1 — Input taxonomy and routing

The original three PDF classes are treated as two technical paths, with a fourth “bad digital-born” condition:

### Path A — trustworthy digital text

A page is digital-born when it has enough extractable text and font evidence and passes the decode-sanity checks. It is read directly into the digital IR and then the `atrium_document` record.

### Path B — OCR-required page

A page is OCR-required when it is image-only, curve-only or its text layer is not trustworthy. The converter records `needs_ocr` rather than invoking an OCR engine itself.

### Prior-OCR text layer

A PDF text layer that is itself the result of an earlier automatic OCR run is not treated as trustworthy born-digital text. The current converter has an explicit `ocr_text_layer` classification and the API contract is intended to expose this as HTTP 422.

The current CLI also distinguishes a minority of prior-OCR pages inside a mixed PDF from a document dominated by such pages. That implementation detail is useful evidence, but the exact production policy for mixed PDFs must be settled in #2 before it is treated as an externally stable API rule.

### Routing rule

The route is therefore:

```text
for each page:
    probe text/font/image evidence
    run decode sanity / text-layer checks
    if trustworthy:
        extract → digital IR → record
    else:
        record `needs_ocr` + reason

if document-level prior-OCR refusal applies:
    return `ocr_text_layer` (422 at the API boundary)
```

No page-classification call is made from this logic. A born-digital converter has a different input modality from the scanned-image classifier.

## §2 — Canonical internal representation

The digital readers should continue to build the repository's digital IR rather than writing the final JSON schema directly from every parser.

The intended layers are:

```text
source bytes
    ↓
digital_pdf.py / digital_docx.py / future format adapters
    ↓
digital_ir.py
    ↓
record construction (`atrium_document.py`)
    ↓
`atrium_document` JSON
```

This separation is important because:

- readers can be replaced without changing downstream record semantics;
- Docling can be an alternative adapter without becoming a second record model;
- format-specific quirks stay at the edge;
- the same geometry can feed both the record and the Markdown renderer.

The record is the contract used by later stages. It should preserve, where available:

- `doc_id` and source provenance;
- `source.sha512`, filename and media type;
- page canvas dimensions / labels;
- text lines with positions and line-level metadata;
- blocks/groups/regions;
- tables;
- `needs_ocr` and its reason on affected pages;
- the program/origin identity needed for the shared document contract;
- paradata once the API service is implemented.

## §3 — PDF/DOCX → Markdown decision

The old issue wording asked whether to use DOCX or HTML as an intermediate format. The current strategy is explicitly different:

```text
PDF/DOCX
   ↓
digital reader / IR
   ↓
atrium_document
   ↓
json_to_md
   ↓
annotated Markdown (optional)
```

### Why this is the chosen route

- The JSON route is already the parity-tested path.
- The record retains geometry that plain Markdown would otherwise lose.
- Markdown can be regenerated whenever the renderer changes without re-reading the source PDF/DOCX.
- The same layout vocabulary is available to TEITOK/ALTO-derived input through the existing layout renderer.
- Page citations can be based on explicit page boundaries in the derived document.
- The production service can return the record as the primary result and offer Markdown only when requested.

### HTML

HTML is still a reasonable local intermediate for a specialized DOCX reader, but it is not a production contract and should not be inserted between PDF and `atrium_document` without a measured reason.

### Markdown cue vocabulary

The existing cue vocabulary remains useful as a deliberately small machine-readable layer inside human-readable Markdown. Relevant cues include `PAGE_BREAK`, `DOC_META`, `BBOX`, `FONT`, `STYLE`, `LAYOUT_COLUMN`, margins/alignment, header/footer boundaries, footnotes, table structure and OCR provenance.

The cue vocabulary should remain additive: the authoritative spatial data is still in the JSON record.

## §4 — Tooling and dependency policy

The implementation should stay permissive-first and avoid pulling heavyweight OCR/VLM stacks into the normal digital image.

| Concern                             | Current direction                                               | Reason                                                                                                  |
|:------------------------------------|:----------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------|
| PDF text/geometry                   | `pdfplumber` + the current digital PDF adapter                  | MIT, light, geometry-aware, suitable for the baseline route.                                            |
| PDF low-level checks/render support | current `pypdfium2`/`pypdf` path                                | Needed for page probing and controlled rendering without adopting AGPL PyMuPDF as a service dependency. |
| DOCX                                | `python-docx` and the current lenient package handling          | Gives direct access to paragraphs, styles, tables, headers/footers and page breaks.                     |
| OCR engine                          | external/AMČR-controlled OCR                                    | OCR selection is outside this repository after the 30 September agreement.                              |
| DOC/XLS                             | LibreOffice headless                                            | MPL-2.0; accepted by AMČR as a conditional converter component.                                         |
| Complex PDF                         | opt-in Docling adapter; benchmark candidates may include MinerU | Keep outside the baseline image until project #22 justifies a tier.                                     |
| flexiconv                           | CLI-only optional path                                          | GPL-3.0-or-later; explicitly outside the production service image/AMČR chain.                           |
| PyMuPDF / AGPL tools                | do not make them a baseline service dependency                  | License and service-distribution implications are unnecessary for the settled light route.              |

The heavy-engine adapter must preserve the same digital IR so that parser choice does not create a second record contract.

## §5 — Shared downstream contracts

### 5.1 OCR

`digital-convert` produces page-level `needs_ocr` flags. The route sends those pages to the AMČR OCR connector. `ocr-postprocess` then merges the OCR page results into the existing record.

The merge must:

- keep the same `doc_id`;
- keep the original source identity and digest;
- preserve born-digital pages that do not need OCR;
- replace/re-originate only the authorised OCR page subset;
- write OCR line geometry and quality information according to the successor originator rules;
- leave the resulting record acceptable to the same downstream NLP/TEITOK stage as a fully OCR-originated document.

The converter must not create a second document just because part of the source is OCRed.

### 5.2 Line quality

The current architecture deliberately avoids two definitions of “quality”. `ocr-postprocess` owns the categorisation and scoring semantics, and born-digital lines should be scored through the same common model using an origin-aware additive rule where necessary.

The converter may still perform **text-layer trust checks** such as decode sanity; that is a different concern from the final line-quality category.

### 5.3 TEITOK

For OCR-originated input, ALTO provides the layout plane. For born-digital input there may be no ALTO. The downstream TEITOK writer therefore needs to consume:

```text
pages[].canvas
lines[].bbox
```

from the record. This belongs in `atrium-nlp-enrich`, not as a new TEITOK writer inside digital-convert.

### 5.4 Keywords and translation

`keyword-extract` now owns both statistical and controlled-vocabulary extraction. `nlp-enrich` no longer owns keyword extraction. `translator` consumes the resulting XML/record downstream.

#4 should not add keyword or translation logic merely because the original issue used “LLM-friendly” language.

## §7 — API contract to preserve from the design

The production service in #2 should expose the digital stage as a normal ATRIUM service, not as a repackaged former LLM API.

### Request

The design should support:

- the source file bytes;
- an optional AMČR baseline `document_json` seed;
- a requested derived rendering mode such as Markdown, without making it the default response plane.

### Response

The primary response should contain:

- the resulting `document_json` record;
- run `paradata` / `CreateAction` according to the shared project contract;
- any declared limits/processing metadata required by the common service envelope;
- optional rendered Markdown when explicitly requested.

### Stable errors

At minimum, preserve the agreed semantics for:

- unsupported format/media type;
- invalid/corrupt/encrypted source;
- `source_digest_mismatch` for a seeded byte mismatch;
- `ocr_text_layer` for the explicit prior-OCR refusal;
- upload/reader limits according to the shared limits contract.

The exact HTTP status mapping belongs to the common project registry and the #2 OpenAPI contract. #4 should not invent a second local error taxonomy.

### Identity

The current target identity is:

```text
repository: ufal/atrium-digital-convert
program id: digital-convert
service id: atrium-digital-convert
endpoint: POST /reformat
API image: ghcr.io/ufal/atrium-digital-convert-api
```

The historical `atrium-digital-born-convertor` spelling is obsolete for the production contract.

## §8 — Verification strategy

The verification ladder should move from deterministic conversion tests to seeded route behaviour.

### Layer A — converter unit / fixture tests

- digital-born PDF extracts the expected text and geometry;
- image-only and curve-only pages do not produce fabricated text;
- garbled text triggers the intended `needs_ocr` reason;
- tables/headings/page labels survive where supported;
- DOCX headings, tables, headers/footers and page breaks map into the record;
- `.docm`/`.dotx` handling keeps the accepted package forms working;
- corrupt/encrypted/unsupported inputs fail with deliberate exit/error codes;
- the JSON route remains the sole default conversion path;
- Markdown rendering uses the same record rather than a second source parser.

### Layer B — contract tests

- `ocr_text_layer` is present in the shared registry and only exposes the agreed refusal status;
- `source_digest_mismatch` is added once implemented in #2;
- service OpenAPI identifies the correct service id and `/reformat` endpoint;
- the response carries the required `CreateAction` / paradata fields;
- seeded `doc_id` and `source.sha512` survive the stage.

### Layer C — OCR hand-off tests

Use a fixture with:

1. one clean digital page;
2. one page with unusable/absent text;
3. OCR output for the flagged page.

Verify that the merged result:

- has one document id;
- keeps the clean digital page untouched;
- contains the OCR page from the OCR stage;
- contains line positions for both pages;
- reaches the same downstream quality and TEITOK stages.

### Layer D — seeded E2E

The hub E2E should start from an AMČR-style seed and exercise the actual HTTP service, not only the CLI image. At minimum cover:

- clean PDF;
- DOCX;
- mixed PDF with `needs_ocr`;
- prior-OCR refusal;
- digest mismatch;
- downstream NLP/TEITOK;
- keyword extraction;
- translator compatibility.

The final check should be the same document identity from source seed through all downstream stages.

## §9 — Complex-layout phase / project #22

The existing `digital_docling.py` adapter proves that a heavy parser can be placed behind the digital IR. That is deliberately not the baseline production dependency.

The evaluation phase should compare the light route against one or more heavy engines using the archaeology-specific data and the project #22 methodology. Relevant measures should include, as applicable:

- character / word accuracy for extracted text;
- reading-order correctness;
- table reconstruction;
- page/block/line geometry;
- heading / figure / page-furniture retention;
- downstream NLP/TEITOK usability;
- resource cost and operational reproducibility;
- licence/deployment constraints.

A heavy parser becomes part of a supported production tier only after that evidence is recorded and mapped back into the same digital IR. #4 does not select a complex-layout winner in advance.

## §10 — Repository-specific implementation boundaries

### `atrium-digital-convert`

Own:

- PDF/DOCX/approved born-digital readers;
- digital IR and record construction;
- source identity/sha512 preservation;
- text-layer trust detection;
- `needs_ocr` page flags;
- `ocr_text_layer` refusal;
- optional record→Markdown rendering;
- eventually the `/reformat` API through #2.

Do not own:

- OCR engine selection;
- page-image classification;
- downstream NLP;
- keyword extraction;
- translation;
- a competing quality taxonomy;
- direct service-to-service orchestration.

### `atrium-ocr-postprocess`

Own:

- broad text-bearing/OCR readers;
- OCR categorisation and quality model;
- OCR page-subset merge;
- successor identity of `alto-postprocess`.

Do not own:

- the canonical digital PDF/DOCX structural reader;
- the born-digital source identity;
- orchestration.

### `atrium-nlp-enrich`

Own:

- LINDAT NLP;
- TEITOK;
- record projection and layout consumption.

Do not own keyword extraction anymore.

### `atrium-keyword-extract`

Own both statistical and controlled keyword extraction. The controlled path is still a research/partial-service feature in the current release, but that state does not change #4's converter boundary.

### `atrium-page-classification`

Remain the scanned/image-originated page classifier. The digital converter does not invoke it.

### `atrium-translator`

Remain the downstream translator. No converter-specific implementation is required here beyond record compatibility.

### `atrium-project`

Own the shared schema/error/service contracts, release gates, E2E infrastructure and document-understanding evaluation framework.
