# Strategy — A document type for each PDF page and document, from text and image (from [page-classification#58](https://github.com/ufal/atrium-page-classification/issues/58))

> _Drafted **2026-11-05** at `v1.4.4-beta` (the checkout's head `1ef3911`). This plan has no issue of its own yet. It
> is this repository's part of the cross-repository plan for decision models, anchored on
> [page-classification#58](https://github.com/ufal/atrium-page-classification/issues/58) and its
> [plan](https://github.com/ufal/atrium-page-classification/blob/test/agent_dev_logs/plans/58.plan.md). It reuses the
> AMČR samples of [#5](https://github.com/ufal/atrium-digital-convert/issues/5). Nothing has been run._

**Status**: 🧪 **Exploratory; the type list needs AMČR's agreement before anything reaches the record.**

**The goal:** given an input PDF, return a chosen type for each page and for the document. The type is read from
the page's text *and* its rendered image, by a decision model.

**The type list is new:** it is seeded from AMČR's heslář `dokument_typ` (decided 11-05), not the 11 page categories.
The 11 categories stay page-classification's answer and keep feeding `route_page()`.

## Context

**What a decision model does.** It reads a state (text or JSON, plus up to 4 images) and typed questions, in one
prefill pass. It returns a probability for each allowed option (2–255 per `choice`) and generates no text. The
candidates, in #58's order, are all served at `POST /v1/systemone`:

| Model | Size | Role here |
|---|---|---|
| Clef | 27B | reads images; tried first |
| Clef-Flash | 9B | reads images |
| Strands Decider 2B | 1.9B | reads text; images are experimental. Here it serves only the text-only ablation |

**What `/describe` already gives per page** (`api_util/digital_report.py:build_report`, `:414`):
- the text-layer verdict (`digital`, `garbled`, `ocr`, `none`, `blank`);
- page-classification's label with its top 3 (`category`, from `service/stages.py:run_page_classification`, `:367`);
- ocr-postprocess's quality;
- the layout counts (`_layout`: lines, blocks, tables, headings, columns, images, vector paths, words, damaged
  words);
- a route (`nlp`, `ocr`, `htr`, `none`) with its reason, from the deterministic `route_page()` (`:315`).

What it does not give is **what kind of document the page is**: a report page, a site photograph, a trench plan, a
map, an object drawing.

**Constraints.**
- **Ownership:** `pages[].category` and `page_categories` belong to page-classification (`BLOCK_FIELD_OWNERS`), and
  the record has no document-type field. The type can live in the report, not the record.
- **Images:** nothing in the production path renders pages today. pypdfium2 is a declared component (Apache-2.0)
  and renders them (`page.render(scale=dpi/72).to_pil()`, as in `tools/samples_report.py`). The schema allows
  rendered images only as recipes in `regenerable`, never as stored files.
- **Settings:** a backing service goes in `.env.example` §3, and a knob in `tool_limits.LIMITS`, the
  `service/README.md` Limits table and `.env.example`. `tests/test_env_contract.py` and
  `tests/test_limits_contract.py` check them.
- **Licences:** a logged component needs a `para_config.txt` row. The Docling weights rows are the precedent.
- **Privacy:** the 15 AMČR PDFs are on the cluster only, and the outputs derived from them stay private (counts
  only; #5, motyc 10-22).

**Two levels.**
- The `group` column is a second, coarse `choice` (6 options) asked in the same request.
- Two-level answers are checked for consistency. The flat 32-way choice and the two-level one are compared as an
  ablation.
- **Why both:** the text types (fieldwork report, client report, brief report…) can rarely be told apart from one
  inner page. They can be told apart from the title page. A page may answer `text` with confidence and its exact
  type with little.

**What AMČR is asked** (on the thread, through #58's comment):
1. Is `dokument_typ` the right list?
2. Should the 9 data types stay out?
3. Can the catalogue type of each sample PDF serve as gold?

A `document-type` scheme in the hub's `atrium_vocab.py`, mapped exactly to these URIs, follows only with that
agreement. It is a class-(c) change in `docs/shared_components.md`.

## Phase B: the stage

`service/stages.py` gets a third stage, **`document-type`**, beside `page-classification` and `ocr-postprocess`.
`run_page_decision()` mirrors `run_page_classification()`:
- the same status set (`ok`, `partial`, `not_configured`, `not_requested`, `skipped`, `unavailable`, `error`,
  `rejected`);
- `_post`-style handling: no error escapes;
- a `service_version`-style probe of the server.

**Per page:**
- **Image:** render with pypdfium2, long side ≤ 1024 px, JPEG. The size is a `tool_limits` setting (see below).
- **State** (JSON, numbers computed in code):
  - `text_layer`;
  - the `_layout()` counts;
  - the body text without its header and footer regions, cut to a set number of characters;
  - page-classification's label and confidence, when that stage ran.
  - The text is untrusted input.
- **Questions:** `group` (6) and `document_type` (32), from `decisions/document_type.v0.json`.

**Per document:** one request with the first ≤ 4 rendered pages and the opening text, asking `document_type`. The
per-page answers are reported beside it, with no rule merging them until the evaluation shows which is right.

**Which pages** follow the existing `classify_pages` choice (`needs_ocr`, furniture-only, or `all`;
`service/describe.py:105-109`), with `all` as the default for this stage.

**Interfaces.**
- **Opt-in through `--stages` / `stages`:** the default stage set is unchanged, so every existing report and test
  stays as it is.
- **The CLI and the service** pass the same arguments (`api_util/digital_to_json.py`, `service/describe.py`), and
  `tests/test_cli_service_parity.py` covers the new stage.
- **Report fields:**
  - `PageReport.document_type`: `{group, label, uri, confidence, top, lane, status, source}`;
  - `summary.document_type` (the document-level answer);
  - one `StageOutcomeModel` entry.
- **The spec:** regenerate `service/openapi.json`
  (`python atrium_openapi.py export --app service.api:app --out service/openapi.json`).
- **Settings:**
  - `DECISION_MODEL_URL`, in `.env.example` §3 (backing services);
  - `DECISION_MODEL_NAME`;
  - `DECISION_TIMEOUT_S` and `DECISION_IMAGE_MAX_SIDE`, as `tool_limits` limits.
- **Paradata:** a `para_config.txt` row for the model (Apache-2.0, `conditional`); the model revision, the
  question-set digest and the thresholds in `config`.
- **`route_page()` does not change.** The type informs a person or a later rule. It does not route.
- **The record does not change.** Nothing is written to it until (a) the `document-type` scheme exists and (b)
  atrium-project#71 grants digital-convert a field for it, such as a page-level type with its source.

## Phase C: evaluate on the AMČR samples (cluster, counts only)

**Data:** the 15 PDFs (2,514 pages) in `/lnet/work/projects/atrium/digital_born_samples`. Page-classification's
labels for them are in `data_samples/reports/describe/all/`:

| Label | `PHOTO` | `LINE_P` | `DRAW` | `TEXT_P` | `DRAW_L` | `TEXT`, `TEXT_T`, `PHOTO_L`, `LINE_T` |
|-------|--------:|---------:|-------:|---------:|---------:|--------------------------------------:|
| Pages |     798 |      608 |    482 |      436 |      176 |                                    14 |

**Gold.**
- **Document level:** the AMČR catalogue's `dokument_typ` for each CTX document. That is 15 labels: enough to catch
  gross failures, too few for a rate.
- **Page level:** 300 pages stratified by those labels, with every page of the rare labels, annotated by AMČR or
  ARÚP/ARÚB with the written definitions. A double-annotated batch of 50 measures agreement.
- Model output is never used as gold.

**Runs:**
- **Inputs:** text only, image only, and both. This shows what the image adds.
- **Models:** Clef, then Clef-Flash; Strands on text only.
- **Structure:** flat against two-level.

**Metrics:**
- accuracy and macro-F1 per level, and the confusion matrix by group;
- Brier and ECE, and coverage against error for the `review` lane;
- the agreement of the page type with page-classification's label (e.g. a photograph type on a `PHOTO` page);
- latency per page and per document, and image-request time, measured separately (early image requests were slow);
- `invalid` answers and timeouts.

**Fixtures:**
- `tools/stage_stub.py` answers `/v1/systemone` with fixed probabilities.
- `tests/fixtures/digital/` PDFs (`image_only.pdf`, `table.pdf`, `two_column.pdf`, …) drive `tests/test_describe.py`
  over real HTTP, as for the other stages.

## Done criteria

- [ ] The v0 list is generated with its provenance, and AMČR has answered on the list (or the question is recorded
      as open).
- [ ] The stage runs from the CLI and the service with identical output; the stub covers every status.
- [ ] The text, image and both runs are scored on the page gold, and the document level on the catalogue types.
- [ ] Image size and latency are measured; thresholds for the lanes are set on a dev half.
- [ ] A recommendation is recorded (stop, keep in the report, propose the scheme and field); the record unchanged.

## Out of scope

- Writing `pages[].category` or `page_categories` (page-classification's), or any record field before #71 grants
  one.
- Changing `route_page()` or the default stage set.
- Publishing sample-derived outputs.
- Hosted inference on archive pages without a data-governance check.

## Refresh conditions

Refresh after any of these:
- AMČR's answer on the list;
- the first stub-backed implementation;
- the first scored run;
- a change of candidates in #58.
