## Execution plan

### Phase 0 — setup on the cluster (once)

```bash
export ATRIUM=/lnet/work/projects/atrium
cd $ATRIUM/GITHUB                     # clone the missing ones with: git clone -b test https://github.com/ufal/<repo>.git
cd atrium-digital-convert && git pull                               # the branch with tools/samples_report.py
python3 -m venv venv-dc                                             # Python 3.11 or newer
venv-dc/bin/pip install -r requirements.txt -r requirements_digital.txt \
    -r service/requirements.txt -r requirements-test.txt
# Docling (GPU runs; CUDA torch from PyPI, several GB) and its models:
venv-dc/bin/pip install -r requirements_digital_docling.txt
venv-dc/bin/docling-tools models download layout tableformer -o $ATRIUM/cache/docling-models
cp ~/issue5_samples_job.sh .                                        # the job (untracked)

# /describe with the real stages (61, 62). Without them those two stages are skipped, not failed.
cd ../atrium-page-classification && git pull
python3 -m venv venv && venv/bin/pip install -r setup/requirements.txt -r service/requirements.txt
cd ../atrium-ocr-postprocess && git pull && bash setup/setup_api_server.sh   # venv-ocr, LayoutReader v3, fastText
```

- **Models.** Both stages fetch their models from the Hugging Face Hub on their first start, and the job allows `WARMUP_S` (1800 s) for that:
  - page-classification: the five v*.4 models into `model/`;
  - ocr-postprocess: Qwen2.5-0.5B and LayoutReader into `HF_HOME`, which the job sets to `$ATRIUM/cache`.

  Run the job once on a node that can reach the Hub, or start each service once by hand beforehand.

### Phase A — the run

```bash
cd $ATRIUM/GITHUB/atrium-digital-convert
# 2-minute smoke on the smallest file, no queue (a login node is enough for one 2 MB file):
DOCS=CTX200914045 ONLY=02_inventory,10_cli_light,50_describe_none SKIP_TESTS=1 bash issue5_samples_job.sh
sbatch -p gpu-troja,gpu-ms --gres=gpu:1 issue5_samples_job.sh        # GPU + CPU: everything
sbatch --time=2-00:00:00 issue5_samples_job.sh                       # CPU only (cpu-troja,cpu-ms)
squeue -u $USER; tail -f dc-issue5.<jobid>.*.out
less $ATRIUM/digital_born_runs/issue5_gpu/report/summary.md          # issue5_cpu for the CPU run
```

- **The stages' limits.** The job starts page-classification and ocr-postprocess on 127.0.0.1 with their limits raised to the inventory:
  - `MAX_UPLOAD_MB` = `STAGE_MAX_UPLOAD_MB` (2048);
  - page-classification `MAX_PDF_PAGES` = the most pages.

  `MAX_IMAGE_PIXELS` stays at the default, so a too-large page shows up as it would in the pilot; `PC_MAX_IMAGE_PIXELS` raises it for a re-run with `FORCE=61_describe_stages,62_describe_all`.
- **Resuming.** A re-submit resumes, per document and per stage. `FORCE=<stage>` redoes one stage, `ONLY=<stage>,…` runs a subset, `DOCS=<doc>,…` a subset of PDFs. `scancel` or Ctrl-C stops the job and its services.
- **On the laptop** (the PDFs are also in `~/PycharmProjects/alto/digital_born_samples`), the same script with paths set:

  ```bash
  REPOS=~/PycharmProjects/alto SAMPLES=~/PycharmProjects/alto/digital_born_samples \
  DC_VENV=~/PycharmProjects/alto/atrium-digital-convert/venv-llm OP_VENV=~/PycharmProjects/alto/atrium-ocr-postprocess/venv-alto \
  OUT=~/PycharmProjects/alto/digital_born_runs/issue5_laptop bash issue5_samples_job.sh
  ```
- **What comes back:** the `report/` folder of the run. `summary.md`, `limits.md`, `candidates.md` and the thumbnails are enough to continue here; `deliver/` holds the JSONs for Dana.

### Phase B — the uncovered case, measured
1. **Read `report/candidates.md`.** It has the candidates under the measured rule (coverage ≥ 0.85, at most 200 body characters), each with a thumbnail, page-classification's category (from `62_describe_all`) and today's route, plus the count grid under other thresholds. `page_signals.csv` has every page.
2. **Review the thumbnails with Dana:** which candidates are scans with a stamp or header (true), and which are real born-digital pages, such as a full-page photo with a caption (false). Choose the thresholds, and whether a graphical category (`DRAW`, `PHOTO`) exempts a page.
3. **Then the marking.** Recommended: (ii).
   - `/describe`'s `route` becomes `ocr` with the reason "little text over a full-page image (coverage x, n characters)", in `api_util/digital_report.py`.
   - The coverage is computed in `digital_pdf.py` beside the image count. The thresholds are POLICY limits in `tool_limits.py`, like `ROUTE_TRASH_SHARE`.
   - The stored record stays `digital`, as the schema's `needs_ocr` invariant requires.

   (i), a new `text_layer` value, only if AMČR needs the mark in the record: a hub schema change plus six revendors.

### Phase C — limits
4. **Propose the pilot values** from `report/limits.md`:
   - `MAX_UPLOAD_MB` (at least 160), with the measured memory per job;
   - `STAGE_TIMEOUT_S`: the slowest stage call × 1.5;
   - `MAX_PAGES`;
   - page-classification `MAX_UPLOAD_MB` / `MAX_PDF_PAGES` / `MAX_IMAGE_PIXELS`;
   - ocr-postprocess `MAX_UPLOAD_MB`.

   Ask AMČR on the thread. Then record this repository's values in `service/README.md` and `.env.example`, and the stages' in their repositories and the hub's `docs/k8s_deployment.md`.

### Phase D — delivery
5. Hand over `report/deliver/` (a record and a `/describe` report per document, plus a README naming each file's source) the way the sharing decision says. Put the per-document table and the limits in a comment.
