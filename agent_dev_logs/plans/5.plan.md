## Execution plan

### Phase A — the run (no code change)
1. Start the `-api` image (or `python -m service.api`) with `MAX_UPLOAD_MB` set above the largest file. `MAX_CONCURRENT_JOBS=1` for clean memory figures. For `/describe`: `STAGE_TIMEOUT_S=600`, `PAGE_CLASSIFICATION_URL` and `OCR_POSTPROCESS_URL` pointing at their `-api` images.
2. For each PDF:
   - `POST /reformat` → the record; `POST /describe` → the report;
   - keep both as `<doc>.document.json` and `<doc>.describe.json`;
   - record the wall time and the server's peak RSS (`/proc/<pid>/status` `VmHWM` before and after, as the 10-08 measurement did).
3. One summary table (Markdown and CSV):
   - document, MB, pages, seconds, peak MB;
   - `text_layer` counts;
   - `needs_ocr` pages with reasons;
   - `/describe` routes (`nlp`/`ocr`/`htr`/`none`);
   - stage statuses (a `unavailable` means `STAGE_TIMEOUT_S` was too low).
4. Deliver the JSONs on the thread (attached, or a filesender link for the full set), with the table in the comment.

### Phase B — the uncovered case, measured
5. **Candidate signals** from the adapter's own data:
   - image coverage per page, the union of `page.images` boxes over the page area, which pdfplumber already returns; the adapter only counts them today (`digital_pdf.py:562`);
   - visible characters and text-box area;
   - the share of characters in furniture (`style.region` header/footer) versus body.

   A page with image coverage ≥ ~0.85 and few body characters is the candidate: a scan with a stamp, header or footer.
6. **Measure, no rule shipped yet:**
   - compute the signals for every `digital` page of the 15 documents (a small script under `tools/`, reading the PDFs with the adapter's pdfplumber settings);
   - list the candidates with page thumbnails for Dana;
   - count what a threshold would catch and what it would wrongly catch among the real born-digital pages.
7. **Then the marking, per the decision on the thread.** Recommended: (ii) `/describe`'s `route` becomes `ocr` with the reason "little text over a full-page image (coverage x, n characters)" in `api_util/digital_report.py`, with the thresholds declared as POLICY in `tool_limits.py`, like `ROUTE_TRASH_SHARE`. The stored record stays `digital`, as the schema's `needs_ocr` invariant requires. (i), a new `text_layer` value, only if AMČR needs it in the record: hub schema plus six revendors.

### Phase C — limits
8. From the table, propose the pilot's values:
   - `MAX_UPLOAD_MB` = the largest file rounded up, with the memory budget it implies per job;
   - `STAGE_TIMEOUT_S` = the longest page-classification call plus margin;
   - `MAX_PAGES` unchanged unless a document exceeds it.

   Ask AMČR to confirm on the thread, then record the values in `service/README.md` and `.env.example`.
