## Context

Issue #2 is the productionization of the born-digital branch after the 30 September repository split. The important change is not simply that the old issue number became `#2`: the surrounding pipeline has changed at the same time.

The current production architecture is:

```text
Scanned / image-originated route
    │
    ├── page-classification
    │       ↓
    └── ocr-postprocess
             │
             └──────────────┐
                            │
Born-digital route          │
    │                       │
    └── digital-convert ────┘  ← common `atrium_document` record contract
                                │
                                ↓
                         quality / NLP / TEITOK
                                │
                                ↓
                         keyword-extract
                                │
                                ↓
                           translator
```

The branch is deliberately **not** implemented as `digital-convert → page-classification → ocr-postprocess`. A born-digital document has no page-image input for page classification, and the current hub digital smoke explicitly protects the rule that OCR post-processing must not touch a digital-born positional plane unless `digital-convert` has marked a page with `needs_ocr`. Routing therefore belongs to the orchestration layer (Temporal / the AMČR route), not to the converter's HTTP app.

The converter's responsibility is to originate the record, make its text-layer verdicts, and expose the metadata that lets the route decide what happens next. `ocr-postprocess` then owns the common reader family and line-quality semantics; `nlp-enrich` owns morphology/NER/TEITOK; `keyword-extract` owns both keyword kinds; translator remains the final XML/translation stage.

## Strategic actions

### A — Freeze the production API contract before implementation

1. **Service identity.** Resolve the current issue-thread question before the first API release. The current proposal is:
   - service id: `atrium-digital-convert`;
   - program id in the record: `digital-convert` (already settled and should not change);
   - API image: `ghcr.io/ufal/atrium-digital-convert-api`;
   - CLI image: keep the existing `ghcr.io/ufal/atrium-digital-convert-digital` role;
   - one authoritative OpenAPI asset for the production API. The historical `openapi-digital.json` bootstrap name should not survive as a competing spec if the final service can use the repository's standard `service/openapi.json` cleanly.

2. **Endpoint.** Implement exactly `POST /reformat` with:
   - multipart `file`;
   - optional `document_json` (AMČR seed or existing baseline);
   - optional `render=md` for the existing Markdown representation;
   - `document_json` in the response;
   - `paradata` as the current Process Run Crate `CreateAction`;
   - the common `limits_applied` response envelope.

3. **Errors.** Keep registered reason semantics stable:
   - 415 `unsupported_media_type` for an unsupported kind, with the reader's `cause`;
   - 422 `ocr_text_layer` for a rejected prior-OCR PDF;
   - 422 `invalid_record` when a supplied record cannot be opened;
   - 422 for readable-but-corrupt/encrypted inputs with their registered cause;
   - 413 for reader/upload/ZIP limits;
   - 422 `source_digest_mismatch` for a seed/source byte mismatch, once registered.

4. **Health / operations.** Wire the existing shared helpers for `/health`, `/ready`, `/info`, `PORT`, `HOST`, SIGTERM drain, upload limits, reader timeout, file/page limits and the same non-root container conventions used by the other current APIs.

5. **Contract tests.** Generate/freeze the production OpenAPI file only after the final identity is confirmed. The API contract test must cover `/reformat`, `paradata`, `document_json`, reason codes, HTTP statuses and the seed profile.

**Done when:** `api-digital` passes the same health/info/API contract/release gate as the other production services, and the first release has the final public identity with no later rename required.

### B — Turn the existing converter into the API's core without duplicating the old LLM service

1. Reuse `api_util.digital_to_json.extract()` and the current document/IR structures rather than rebuilding PDF/DOCX conversion inside the service layer.
2. Replace the inherited LLM `service/api.py` with a thin HTTP adapter around the digital converter.
3. Remove the LLM request endpoints and their remote/local model runtime from the **production API image**. The research/legacy code may remain temporarily in the repository migration branch only as required by #72, but it must not be part of the released `api-digital` target's runtime dependencies.
4. Keep the existing `digital` CLI target as the deterministic conversion reference and make the service call the same Python extraction path, so CLI and HTTP cannot silently diverge.
5. Make the service accept an AMČR seed before conversion and preserve the seed's immutable identity fields.

**Done when:** the same fixture passed to the CLI and `/reformat` yields byte-equivalent record semantics after normal JSON ordering/provenance differences are excluded.

### C — Implement the seed/source integrity handshake

1. When `document_json.source.sha512` is present, hash the **received source bytes** and compare them to the seed value before parsing.
2. On mismatch, return 422 with `reason = "source_digest_mismatch"`; do not mutate the seed or emit a partial record.
3. Register `source_digest_mismatch` in the hub reason-code registry and in the service OpenAPI extension.
4. Add tests for:
   - matching SHA-512;
   - mismatch;
   - missing `sha512` (accepted, because it is optional in the schema);
   - seed `doc_id` different from upload filename;
   - seed filename/media type preservation;
   - source hash persistence after later stage merges.

**Done when:** the seeded route cannot silently process the wrong bytes under a valid AMČR identity.

### D — Complete the born-digital input set around the new reader owner

The current digital PDF/DOCX structural readers should remain the rich geometry path where needed; the generic text-bearing formats should not create a second reader fork.

1. **ODT / RTF / XLSX / ODS:** consume the reader contract owned by `atrium-ocr-postprocess`, using the project's pinned/vendor mechanism rather than an unpinned copy.
2. **PDF / DOCX:** retain `digital-convert`'s richer readers for page canvas, bboxes, structural groups, headings and tables; share the low-level text-layer classification semantics where the common-reader contract requires parity.
3. **DOC / XLS:** add a headless LibreOffice conversion path in the API image. Keep:
   - original source filename and media type in `source`;
   - conversion details in paradata;
   - the resulting semantic record as `digital-convert` output.
4. **Tables:** spreadsheet sheets/cells should map into the existing `tables[]` + `group_id` record shape; do not invent a new spreadsheet-specific block for #2.
5. **Origin:** every accepted born-digital format must resolve to a `digital-born-*` origin that authorises `digital-convert` as the positional originator.
6. **Reader parity:** add fixture tests proving page/line ordering and the source-origin label for every newly supported format.

**Done when:** PDF, DOCX, ODT, RTF, XLSX and ODS all produce valid records; DOC/XLS also succeed through the agreed LibreOffice compatibility path.

### E — Make the text-layer/OCR boundary explicit

There are **two different cases**, and the API contract must keep them distinct.

#### E.1 Page-level `needs_ocr`

For a genuinely born-digital PDF page whose embedded layer exists but fails decode-sanity, or for a PDF page with no usable text layer, the converter writes:

```json
{
  "needs_ocr": true,
  "needs_ocr_reason": "..."
}
```

The converter reports the fact; it does not call OCR and does not decide orchestration.

#### E.2 Document-level `ocr_text_layer`

A PDF whose hidden text is an earlier OCR run is not treated as trustworthy born-digital input. The current implementation refuses the **whole document** when at least 50% of text-bearing pages are identified as prior OCR text layers.

For mixed documents below that threshold, the current converter retains the record and marks the affected pages `needs_ocr` with the explicit prior-OCR reason. Before release, confirm that this 50% threshold is the intended AMČR route rule rather than an accidental implementation default.

#### E.3 Route-level hand-off

The route/orchestration layer should:

1. accept the digital record;
2. inspect `pages[].needs_ocr`;
3. send only those pages to the ATR OCR connector;
4. receive ALTO/page results for those pages;
5. call `ocr-postprocess` with the original record as the baseline;
6. merge only the flagged page positional plane into the record.

The merged record must retain:

- the same `doc_id`;
- the same immutable `source` fields;
- the same `source.origin = digital-born-*` at document level;
- digital-convert ownership for non-OCR pages;
- OCR-derived page/line content only for pages that actually went through OCR.

**Done when:** a mixed record can contain digital-born and OCR-reprocessed pages without changing the document identity or creating a second document.

### F — Apply the common line-quality model through `ocr-postprocess`

1. Do **not** reuse `digital-convert`'s decode-sanity score as the final archive line-quality signal. It is a text-layer trust detector, not the common five-category quality model.
2. Run the authoritative `ocr-postprocess` quality classifier on the born-digital line text as a separate contribution to the same record.
3. Keep field ownership explicit:
   - digital-convert owns born-digital line `text`, `bbox`, `group_id`, `style` and its source-side structural fields;
   - ocr-postprocess owns the common quality/category fields it is granted by the shared record contract;
   - nlp-enrich adds morphology/NER/TEITOK references later.
4. Do not re-attribute the whole `lines` block to ocr-postprocess. The current `atrium_document` ownership model exists specifically to avoid that.
5. Preserve the page-level `needs_ocr` reason independently of the quality category: they answer different questions.

**Done when:** a digital-born line receives the same `Clear | Noisy | Trash | Non-text | Empty` semantics as an OCR-originated line, with no duplicated line rows or originator conflict.

### G — Enable TEITOK from record geometry in `nlp-enrich`

This is a cross-repository dependency, but it is part of #2's production acceptance because a born-digital document does not have ALTO.

1. Define the born-digital layout source as:
   - `pages[].canvas` for page dimensions;
   - `lines[].bbox` for positional lines;
   - `lines[].group_id` / structural `style` for paragraph/heading/table grouping.
2. Extend the `nlp-enrich` service/batch path so it can consume the record's lines without requiring a fabricated ALTO file.
3. Keep TEITOK's facsimile references aligned with the record's `page_index` / page label and the digital line boxes.
4. Continue storing quality/category fields in the record rather than duplicating them into TEITOK unless the existing opt-in projection explicitly requires them.
5. Add a born-digital TEITOK fixture and an end-to-end reference check using the hub's `e2e_assert.py`.

**Done when:** a born-digital PDF/DOCX can reach the normal NLP/TEITOK stage without an ALTO dependency.

### H — Keep keyword extraction and translation downstream and decoupled

No keyword or translation logic should be reintroduced into `digital-convert`.

1. The converter stops at the document record plus its optional Markdown representation.
2. `nlp-enrich` remains the morphology/NER/TEITOK stage.
3. `keyword-extract` consumes the post-NLP record. Its current statistical service is usable; its controlled LLM kind remains a separate follow-up (`atrium-keyword-extract#2`) and should not block the converter's HTTP API contract.
4. `translator` consumes the resulting TEITOK/XML plus `document_json` and contributes its `translations` block and paradata.

**Done when:** the digital branch has no hidden dependency on the former `llm-enrich` service or the former keyword endpoint.

### I — Upgrade the hub tests from CLI proof to production-route proof

Use the existing `e2e-digital-smoke.yml` as the fixture source, but do not make the current CLI smoke the final acceptance test.

Add the following production cases:

1. **Clean PDF / DOCX:** `/reformat` returns a valid record and `paradata`.
2. **AMČR seed:** `doc_id`, `source.sha512`, filename and media type survive the first stage and every later stage.
3. **Wrong digest:** `/reformat` returns 422 `source_digest_mismatch` and writes no output record.
4. **Garbled digital page:** record succeeds with `needs_ocr` on exactly the affected page(s).
5. **Mixed PDF:** verify the confirmed production policy for prior-OCR pages and the 50% threshold decision.
6. **Whole OCR-layer PDF:** `/reformat` returns 422 `ocr_text_layer`; the route retries the original source through the OCR branch instead of forcing it through digital-convert.
7. **OCR subset merge:** the same record contains both untouched digital pages and OCR-reprocessed pages, with preserved `doc_id` / `source`.
8. **Common quality:** born-digital and OCR lines have the same category vocabulary and compatible scores.
9. **NLP/TEITOK:** record geometry produces valid TEITOK without ALTO for the digital branch.
10. **Keyword stage:** current statistical `keyword-extract` can consume the record; the controlled LLM branch is tested separately when it becomes available.
11. **Translator:** final record still validates and retains the upstream blocks + translation output.

The scanned branch remains tested by `e2e-pipeline-smoke.yml`; the digital route should not force scan-only stages into its path.

8. Keep the current CLI `-digital` image as a useful local/batch target, but distinguish it clearly from the production HTTP image.

## Verification / done-criteria

The issue is complete only when all of the following are true:

1. **HTTP service:** `/reformat`, `/health`, `/ready` and `/info` work with the standard ATRIUM service conventions.
2. **Identity:** the service id, image names and OpenAPI asset are the final names used by the hub and will not need a rename after first release.
3. **Seed integrity:** AMČR `doc_id`, `source.sha512`, filename and media type survive; a wrong SHA-512 is a stable 422 `source_digest_mismatch`.
4. **Input coverage:** PDF, DOCX, ODT, RTF, XLSX and ODS work; legacy DOC/XLS work through the agreed LibreOffice path with provenance preserved.
5. **Text-layer handling:** clean digital pages pass; corrupt/ambiguous pages carry `needs_ocr`; prior-OCR PDFs use the confirmed `ocr_text_layer` policy.
6. **OCR merge:** flagged pages can be OCR'd and merged back into the same document record without creating a second document or changing the document-level digital origin.
7. **Quality:** `ocr-postprocess` supplies the authoritative line quality/category fields for born-digital lines using the same semantics as the OCR branch.
8. **NLP/TEITOK:** nlp-enrich consumes the record's native geometry when ALTO is absent and produces a valid TEITOK representation.
9. **Downstream stages:** keyword-extract and translator can consume the resulting record without special-case digital-only branches beyond the layout/input adapter.
10. **E2E:** the hub has a seeded born-digital path with the above cases green, while the scanned path remains green independently.
11. **Release:** the API image passes the standard health, contract, workflow, provenance and release-trust gates; the production image contains the intended digital stack, not the former LLM service.
12. **Documentation:** repository and hub docs describe `digital-convert` as the born-digital production stage and no longer present the old LLM API as its service surface.

## Questions

1. **Confirm the final service identity:** `atrium-digital-convert` + `ghcr.io/ufal/atrium-digital-convert-api` is the current proposal; the old historical `atrium-digital-born-convertor` name should be dropped unless AMČR explicitly requests otherwise.
2. **Confirm the OpenAPI asset filename:** use the repository-standard `service/openapi.json` after replacing the inherited LLM spec, or retain the distinct `service/openapi-digital.json` name from the historical bootstrap. Pick one before the first release.
3. **Confirm the mixed-PDF threshold:** keep the current `OCR_LAYER_DOCUMENT_SHARE = 0.5` rule, or replace it with an AMČR-approved rule. The semantic distinction between whole-document refusal and page-level `needs_ocr` should remain regardless.
4. **Confirm the spreadsheet representation:** one logical page per sheet and line rows/cell grouping through the existing `tables[]` / `group_id` contract is the current implementation proposal.
5. **Confirm the S2 pilot date:** propose the production pin/date before the 11 November meeting, using 31 October as the internal production-runnable target.

## Out of scope

- Page classification of born-digital inputs. It remains part of the scanned/image branch.
- OCR engine development. `digital-convert` only detects/flags pages and emits the hand-off metadata; ATR/OCR remains an external production service.
- Replacing the `ocr-postprocess` quality model with another model.
- Rebuilding the generic text reader independently in digital-convert. Its shared reader ownership is #72 / `ocr-postprocess`.
- Keyword extraction implementation beyond producing a record that downstream `keyword-extract` can consume. Controlled LLM keyword work is `atrium-keyword-extract#2`.
- Custom NER or annotation tooling (`atrium-nlp-enrich` issues outside the digital route).
- Complex PDF layout research (Docling/MinerU) as a required production dependency. Keep it optional and separate from the baseline API image.
- Record-only mode, which remains deferred under the pilot contract.
- Rewriting historical records. The successor map and origin rules exist so older `alto-postprocess` / `llm-enrich` stamps remain readable without re-attribution.
