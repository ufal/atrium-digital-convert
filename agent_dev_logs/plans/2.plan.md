## Context

The born-digital path is no longer a standalone converter. It is the first/originator stage of the six-stage ATRIUM production chain after the repository split:

```text
page-classification
→ ocr-postprocess
→ nlp-enrich
→ keyword-extract
→ translator
```

with the born-digital route entering through:

```text
api-digital /reformat
→ page-classification
→ ocr-postprocess
→ nlp-enrich
→ keyword-extract
→ translator
```

and with pages requiring OCR temporarily handed to the ATR/OCR route and merged back into the same `atrium_document`.

The production repository set now is:

```text
atrium-page-classification
atrium-ocr-postprocess
atrium-digital-convert
atrium-nlp-enrich
atrium-keyword-extract
atrium-translator
```

The hub `atrium-project` owns the common schema, service contract modules, seed rules, successor map, E2E tests and release gates.

The 2026-09-30 meeting also changed two identifiers that are load-bearing for the implementation:

1. the production endpoint is **`/reformat`**, not `/convert`;
2. the service identity is the destination identity **`atrium-digital-born-convertor`**, even while the repository rename is completed separately.

Do not reintroduce `/convert` as the primary production route.

# Strategic actions

## A — Freeze the `/reformat` service contract first

### A.1 Service identity

Use these identities from the first API release:

```text
service:    atrium-digital-born-convertor
program:    digital-convert
endpoint:   /reformat
OpenAPI:    service/openapi-digital.json
asset:      openapi-digital.json
```

The repository can still be renamed after the API is working. The rename must not create another service identity migration.

The release gate must therefore treat the first `openapi-digital.json` as the service's own baseline.

### A.2 Request shape

Implement multipart input:

```text
POST /reformat
Content-Type: multipart/form-data

file=<born-digital file>
document_json=<optional AMČR seed>
render=<optional representation request, initially md>
```

The service must not require callers to construct a temporary path or pre-convert the file.

### A.3 Seed semantics

When a `document_json` seed is supplied:

1. parse it with the common record validator;
2. preserve the seed `doc_id`;
3. preserve source filename/media type;
4. verify `source.sha512` against the uploaded bytes;
5. refuse mismatches with `422` and `reason: source_digest_mismatch`;
6. let the actual document reader write `source.origin`;
7. never create a second document identity.

`source.sha512` is an input integrity check, not a replacement for paradata.

### A.4 Response shape

The canonical response should contain:

```text
doc_id
record
paradata
```

and optionally:

```text
markdown
```

when the caller requests the derived Markdown representation.

The `record` is authoritative. Markdown is derived and must never become an alternative representation with independently generated text.

### A.5 Error contract

Implement these stable mappings:

```text
415 unsupported_media_type
422 invalid_record
422 ocr_text_layer
422 source_digest_mismatch
422 encrypted
422 corrupt
413 limit_exceeded
500/503 operational/service failure
```

Where a converter-specific failure is useful, retain it as `cause` without inventing a new top-level public reason for every parser exception.

### A.6 Limits and operational surface

Use the existing common service machinery for:

```text
/health
/health?deep=true
/ready
/info
```

and environment-configured limits.

At minimum `/info` must expose:

* service/program identity;
* supported media types;
* effective limits;
* readiness;
* API version;
* implementation/version information.

Do not build an independent health/error framework.

## B — Build `api-digital` as a separate production image

The current repository has an important split that must be preserved:

```text
base
  ├── remote / llm     # research / former LLM implementation
  └── digital          # born-digital converter
          └── api-digital
```

`api-digital` must be built from the light `digital` stage.

Do **not** turn the existing LLM `api` target into the born-digital API.

The production image must not contain:

* the former OpenRouter/Ollama service stack;
* vLLM/transformers research dependencies;
* model weights;
* the heavy Docling production path.

The light converter remains the production baseline.

The optional heavy Docling/MinerU path remains research/local-only and must not delay the production API.

### B.1 Docker target

Add:

```text
FROM digital AS api-digital
```

with the service entry point running the new FastAPI application.

The first release should publish the destination service identity even before the repository rename.

### B.2 CI

Update the Docker workflow so that:

```text
build-targets = [..., api-digital]
probe-targets = [..., api-digital]
```

The API target must pass the same health/contract probe pattern used by the existing production services.

The old LLM `api` target may remain temporarily for the repository transition, but it must not be the image pinned for the born-digital production stage.

## C — Add all AMČR born-digital formats

### C.1 Native/light readers

The production API must cover:

```text
PDF
DOCX
ODT
RTF
XLSX
ODS
```

The current direct implementation is mainly PDF/DOCX. The missing formats should be consumed through the document-reader implementation now owned by `atrium-ocr-postprocess`.

Do not copy the reader by hand and maintain a second implementation.

Vendor the required reader code with:

* exact source/revision pin;
* provenance entry;
* parity test against the owner;
* `para-drift` enforcement.

### C.2 DOC / XLS through LibreOffice

Handle:

```text
.doc → LibreOffice → .docx → common reader
.xls → LibreOffice → .xlsx → common reader
```

The original input remains authoritative in the record:

```text
source.name
source.media_type
```

The conversion step is recorded as processing/provenance information rather than silently replacing the source.

LibreOffice is a declared conditional component in `para_config.txt`.

### C.3 Normalised record shape

For all formats, the converter must produce the same conceptual record:

```text
document
  ├── pages[]
  │     ├── page identity/index
  │     ├── canvas
  │     ├── needs_ocr
  │     └── lines[]
  │           ├── text
  │           ├── bbox
  │           └── line/page identity
  ├── content
  └── tables[]
```

The exact schema remains hub-owned.

Do not add a born-digital-only schema fork.

## D — Make text-layer/OCR routing explicit

### D.1 Text-layer rule

A PDF is accepted as born-digital only when its text layer is usable.

Reject/refuse a prior OCR text layer with:

```text
HTTP 422
reason: ocr_text_layer
```

This rule remains intentionally conservative: OCR text is not trusted as a born-digital source.

### D.2 Per-page `needs_ocr`

The converter must preserve page-level state.

A page without a usable text layer is not silently converted into an empty success.

The record must contain enough information for the next stage to determine:

```text
page_index
page label
needs_ocr
needs_ocr_reason
canvas
```

### D.3 OCR hand-off

When a document contains a mixture of digital and scanned pages:

```text
api-digital
  → record with digital pages
  → needs_ocr pages identified
  → ATR/OCR path processes those pages
  → ALTO returned for those pages
  → ocr-postprocess merges them back by page identity
```

Do not create a second document record for the OCR subset.

The final record must retain the original:

```text
doc_id
source.sha512
source.name
```

### D.4 Merge contract

The merge should be defined around stable page identity:

```text
page_index / page label
```

The merge must replace/add content only for the OCR-required pages and leave born-digital pages untouched.

Add a mixed-document fixture proving:

```text
digital page
+ scanned page
+ digital page
```

becomes one valid record.

## E — Unify quality scoring with `ocr-postprocess`

The current converter already computes extraction/decode diagnostics. Keep those diagnostics for routing and debugging, but do not make them a second production categorisation system.

The production rule is:

```text
digital extraction
       │
       ▼
same record
       │
       ├── OCR pages merged
       │
       ▼
ocr-postprocess
       │
       ├── line categorisation
       └── quality_score
```

`ocr-postprocess` owns the authoritative line-quality semantics for both OCR and born-digital text.

### E.1 Shared module

Add/extend the shared post-processing mechanism so that the scorer can operate on `lines[]` from a born-digital record.

The scorer must write:

```text
lines[].categ
lines[].quality_score
```

but must not take ownership of the record's source/originator plane.

### E.2 Successor-aware program identity

Because the old repository was `atrium-alto-postprocess` and the new owner is `atrium-ocr-postprocess`, use the hub successor map everywhere rather than hard-coding one name.

The current successor map must continue accepting:

```text
alto-postprocess → ocr-postprocess
llm-enrich       → keyword-extract
```

until the contract freeze.

---

## F — Make record geometry usable by `nlp-enrich`

The old fallback was text-only TEITOK when no ALTO existed.

That is no longer sufficient for the born-digital production path.

### F.1 Required input

`nlp-enrich` must be able to create TEITOK directly from:

```text
pages[].canvas
lines[].bbox
page / line ordering
```

when ALTO is unavailable.

### F.2 Ownership

The TEITOK reader remains owned by `atrium-nlp-enrich`.

The born-digital converter may vendor the exact reader/geometry helpers when needed, with a pinned copy and `para-drift` parity.

### F.3 Fixture

Add a born-digital PDF record fixture containing:

* at least two pages;
* line bounding boxes;
* a page break;
* stable line ordering.

The expected TEITOK output must preserve page/line geometry.

---

## G — Record → Markdown is derived output

The existing visual Markdown route is useful to keyword extraction and document-level consumers.

Promote it into the born-digital design as:

```text
record
  → record_to_markdown
```

not:

```text
PDF
  → independent markdown parser
```

The record must remain the single source of truth.

Support:

```text
render=md
```

for clients which need the derived form.

The Markdown representation should preserve:

* page sections;
* page breaks;
* line geometry cues where requested;
* tables;
* headings;
* OCR provenance markers when present.

The record and its Markdown must therefore remain regenerable from one another through the same owned renderer rather than separate extraction paths.

## H — Integrate the six-stage API chain

The authoritative production service map is:

| Stage                     | Repository / image                     | API                          |
| ------------------------- | -------------------------------------- | ---------------------------- |
| page categories           | `atrium-page-classification` → `…-api` | `/predict_document`          |
| OCR output / scoring      | `atrium-ocr-postprocess` → `…-api`     | `/process`                   |
| born-digital              | final digital-convertor image          | `/reformat`                  |
| morphology / NER / TEITOK | `atrium-nlp-enrich` → `…-api`          | `/enrich`, `/project_record` |
| keywords                  | `atrium-keyword-extract` → `…-api`     | `/extract_keywords`          |
| English metadata          | `atrium-translator` → `…-api`          | `/translate`                 |

For the born-digital E2E, establish:

```text
/reformat
   ↓
/predict_document
   ↓
/process
   ↓
/enrich /project_record
   ↓
/extract_keywords
   ↓
/translate
```

with the OCR subset routed through the ATR/OCR path before the `/process` merge/score step.

The six service contracts must all use the same:

* health conventions;
* error envelope;
* OpenAPI generation;
* provenance conventions;
* `CreateAction`;
* `doc_id` / `source.sha512` preservation.

## L — Release and deployment hardening

`api-digital` is not production-ready merely because the FastAPI code works.

Before the production tag:

1. service image must have its final intended identity;
2. OpenAPI asset must be attached to the release;
3. image provenance must point to the immutable release;
4. release tag immutability must be active;
5. production workflow reusable-action references must follow the #72 release-trust rules;
6. the service must pass the hub Docker/API probe;
7. the seeded E2E must be green.

The current `atrium-project#72` work on immutable release artifacts and production image identity therefore remains a prerequisite to calling the October build production-ready.

# Verification / done-criteria

1. **API identity:** the production endpoint is `/reformat`, with service id `atrium-digital-born-convertor` and program id `digital-convert`.
2. **Input coverage:** all AMČR-supported formats are accepted or receive a documented registered refusal.
3. **Seed integrity:** matching `source.sha512` succeeds; mismatch returns `source_digest_mismatch`.
4. **OCR safety:** unusable/prior OCR text layers return `ocr_text_layer` instead of silently becoming digital-born text.
5. **Mixed documents:** native and OCR-recovered pages coexist in one valid `atrium_document`.
6. **Quality parity:** born-digital lines use the same authoritative quality categorisation as OCR lines.
7. **Geometry parity:** TEITOK can be generated from record positions when ALTO is unavailable.
8. **Downstream parity:** the record reaches NLP, keywords and translation without a born-digital-specific schema branch.
9. **Provenance:** every successful `/reformat` call returns a valid `CreateAction`.
10. **Operational parity:** health, ready, info, limits and errors follow the same service conventions as the other production APIs.
11. **OpenAPI:** `openapi-digital.json` is committed, generated from the service and released as an asset.
12. **Container parity:** production `api-digital` contains the converter stack only; research LLM dependencies remain outside the production target.
13. **CI:** build and probe jobs exercise `api-digital`.
14. **E2E:** the seeded born-digital pipeline is green through the six production stages.
15. **Release trust:** the pinned artifact is immutable and its provenance identifies the actual production release.
16. **Pilot readiness:** the concrete production/S2 date is available for the 11 November meeting, with the service already runnable by the end-of-October target.
