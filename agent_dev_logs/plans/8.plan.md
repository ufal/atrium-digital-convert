**The goal:** given an input PDF, return a chosen type for each page and for the document. The type is read from
the rendered page images alone, by a decision model.

**Form, not content (2026-11-09).** `dokument_typ` says what a document *is* (a report, a site photograph, a trench
plan, a map), not what it is about. Under the umbrella's rule, form is decided by the tools that see images (this
repository, page-classification) and content by those that read text (keyword-extract, ocr-postprocess). So:
- no request carries text (the text layer, the body text) or another tool's answer (page-classification's label);
- the layout counts and page-classification's label are compared with the answers in the evaluation, never sent;
- a written genre (field report, annex, expert or client report, brief report, other text) is asked only of a
  document, whose title page shows it, never of an inner page.

**The type list is new:** it is seeded from AMČR's heslář `dokument_typ` (decided 11-05), not the 11 page categories.
The 11 categories stay page-classification's answer and keep feeding `route_page()`.

## Context

**What a decision model does.** It reads a state (text or JSON, plus up to 4 images) and typed questions, in one
prefill pass. It returns a probability for each allowed option (2–255 per `choice`) and generates no text. The
candidates, in #58's order, are all served at `POST /v1/systemone`:

| Model              | Size | Role here                                                                  |
|--------------------|------|----------------------------------------------------------------------------|
| Clef               | 27B  | reads images; tried first                                                  |
| Clef-Flash         | 9B   | reads images                                                               |
| Strands Decider 2B | 1.9B | reads text; images are experimental. Here only if its vision extra answers |

**What `/describe` already gives per page** (`api_util/digital_report.py:build_report`, `:414`):
- the text-layer verdict (`digital`, `garbled`, `ocr`, `none`, `blank`);
- page-classification's label with its top 3 (`category`, from `service/stages.py:run_page_classification`, `:367`);
- ocr-postprocess's quality;
- the layout counts (`_layout`: lines, blocks, tables, headings, columns, images, vector paths, words, damaged
  words);
- a route (`nlp`, `ocr`, `htr`, `none`) with its reason, from the deterministic `route_page()` (`:315`).

What it does not give is **what kind of document the page is**: a report page, a site photograph, a trench plan, a
map, an object drawing.

**Constraints.**
- **Ownership:** `pages[].category` and `page_categories` belong to page-classification (`BLOCK_FIELD_OWNERS`), and
  the record has no document-type field. The type can live in the report, not the record.
- **Images:** nothing in the production path renders pages today. pypdfium2 is a declared component (Apache-2.0)
  and renders them (`page.render(scale=dpi/72).to_pil()`, as in `tools/samples_report.py`). The schema allows
  rendered images only as recipes in `regenerable`, never as stored files. _(superseded 11-11: `regenerable` leaves the record, D1)_
- **Settings:** a backing service goes in `.env.example` §3, and a knob in `tool_limits.LIMITS`, the
  `service/README.md` Limits table and `.env.example`. `tests/test_env_contract.py` and
  `tests/test_limits_contract.py` check them.
- **Licences:** a logged component needs a `para_config.txt` row. The Docling weights rows are the precedent.
- **Privacy:** the 15 AMČR PDFs are on the cluster only, and the outputs derived from them stay private (counts
  only; #5, motyc 10-22).

## Phase A: the type list (draft; v3 since 2026-11-09, images only, one view per level)

`decisions/document_type.v3.json`, generated by `tools/build_document_types.py` from keyword-extract's vocabulary data
(`data_samples/vocab/amcr_flat.json`, scheme `dokument_typ`, 41 terms). The file records the source commit and the
SHA-256, and its `scope`: form, read from page images only.

**One view per level (v3, 2026-11-09).**

| View           | Level    | Input                               | Questions                                                                                   | Digest      |
|----------------|----------|-------------------------------------|---------------------------------------------------------------------------------------------|-------------|
| `pdf_page`     | page     | one rendered page                   | `group` (6) and `image_type` (25 picture types + `unspecified`, also the answer for text)   | `a7e3cf74…` |
| `pdf_document` | document | the first rendered pages, at most 4 | `group` (6) and `document_type` (all 32, the 6 written genres among them)                   | `6c5e8abb…` |

- **Why two views:** an inner page of a report rarely shows its genre; a title page does. A page therefore answers
  its medium (`group`) and, if it is a picture, its picture type; a document answers its full type.
- **Every option is an AMČR term** (P1 of keyword-extract#2): `unspecified` (`neurčený dokument`) is both the abstain
  option and a text page's `image_type`. A row's `consistent` column says whether the type falls in the chosen
  group.
- **The wording** names no input ("What kind of document is this, broadly?", "Which AMČR document type is this?",
  "If this is a photograph, an aerial photograph, a plan, a map or a drawing, which AMČR document type is it?");
  each view's `item` and `inputs` say what the request carries. Both views' `inputs.text` is `none`, and the CLI
  refuses a view that says otherwise.
- **Ownership:** this repository owns the list. Since v3 no repository vendors it: keyword-extract reads text, so it
  decides content, not form (#3). page-classification's track 2 (#58) is to vendor the picture types, which needs a
  release with v3; the hub's `docs/shared_components.md` row returns then.
- **History:** v0 (11-06) was never run; v1 (11-08) had one question set for both tools; v2 (11-08, round 2) had a
  view per input, a text view for keyword-extract and the text layer on request here; v3 (11-09) is images only.

- ecofact analysis, geodetic, geophysical, GNSS, fieldwork and vector-plan data;
- the three 3D types.

**Two levels.**
- The `group` column is a second, coarse `choice` (6 options) asked in the same request.
- Two-level answers are checked for consistency (`consistent`). The flat choice and the two-level one are compared
  as an ablation.
- **Why both:** the text types (fieldwork report, client report, brief report…) can rarely be told apart from one
  inner page. They can be told apart from the title page. A page answers `text` with confidence and leaves the genre
  to the document level.

## Phase B: the stage

`service/stages.py` gets a third stage, **`document-type`**, beside `page-classification` and `ocr-postprocess`. _(superseded 11-11: parked; and `/describe` calls no other tool, H11)_
`run_page_decision()` mirrors `run_page_classification()`:
- the same status set (`ok`, `partial`, `not_configured`, `not_requested`, `skipped`, `unavailable`, `error`,
  `rejected`);
- `_post`-style handling: no error escapes;
- a `service_version`-style probe of the server.

**The input is the page image, and only the image (2026-11-09).** A request carries rendered pages and nothing
else. The text-layer option of 11-08 is removed: a type is form, and form is not read from text.

**The offline CLI, written first** (`tools/decide_documents.py`, 2026-11-08; images only since 11-09;
`tests/test_decide_documents.py`):
- renders each page with pypdfium2, long side `--max-side` (1024);
- **per page:** the `pdf_page` view (`group`, `image_type`) about one image;
- **per document:** the `pdf_document` view (`group`, `document_type`) about the first ≤ 4 pages (a request's image
  limit);
- writes `DECIDE_PAGES.csv` and `DECIDE_DOCS.csv` (probabilities, `consistent`, `top3`, lane, status, latency,
  digest), a summary and paradata (each view's digest, `inputs: images only`); `--gold` / `--page-gold` score them,
  a written genre given as a page's gold scoring its group only; `--resume`; `--served-on`, never the URL.

**The stage** (after 11-11, if the CLI's results justify it) reuses the CLI's functions: _(superseded 11-11: parked during the pilot phase)_
- **Per page:** the image alone. The `_layout()` counts and page-classification's label are reported beside the
  answer and compared with it in the evaluation; they are not sent.
- **Questions:** the `pdf_page` view of `decisions/document_type.v3.json`; per document, its `pdf_document` view.
- **Per document:** as in the CLI. The per-page answers are reported beside it, with no rule merging them until the
  evaluation shows which is right.

**Which pages** follow the existing `classify_pages` choice (`needs_ocr`, furniture-only, or `all`;
`service/describe.py:105-109`), with `all` as the default for this stage.

**Interfaces.**
- **Opt-in through `--stages` / `stages`:** the default stage set is unchanged, so every existing report and test
  stays as it is.
- **The CLI and the service** pass the same arguments (`api_util/digital_to_json.py`, `service/describe.py`), and
  `tests/test_cli_service_parity.py` covers the new stage.
- **Report fields:**
  - `PageReport.document_type`: `{group, label, uri, confidence, top, lane, status, source}`;
  - `summary.document_type` (the document-level answer);
  - one `StageOutcomeModel` entry.
- **The spec:** regenerate `service/openapi.json`
  (`python atrium_openapi.py export --app service.api:app --out service/openapi.json`).
- **Settings:**
  - `DECISION_MODEL_URL`, in `.env.example` §3 (backing services);
  - `DECISION_MODEL_NAME`;
  - `DECISION_TIMEOUT_S` and `DECISION_IMAGE_MAX_SIDE`, as `tool_limits` limits.
- **Paradata:** a `para_config.txt` row for the model (Apache-2.0, `conditional`); the model revision, the
  question-set digest and the thresholds in `config`.
- **`route_page()` does not change.** The type informs a person or a later rule. It does not route.
- **The record does not change.** Nothing is written to it until (a) the `document-type` scheme exists and (b)
  atrium-project#71 grants digital-convert a field for it, such as a page-level type with its source.

## Phase C: evaluate on the AMČR samples (cluster, counts only)

**Data:** the 15 PDFs (2,514 pages) in `/lnet/work/projects/atrium/digital_born_samples`. Page-classification's
labels for them are in `data_samples/reports/describe/all/`:

| Label | `PHOTO` | `LINE_P` | `DRAW` | `TEXT_P` | `DRAW_L` | `TEXT`, `TEXT_T`, `PHOTO_L`, `LINE_T` |
|-------|--------:|---------:|-------:|---------:|---------:|--------------------------------------:|
| Pages |     798 |      608 |    482 |      436 |      176 |                                    14 |

**Gold.**
- **Document level:** the AMČR catalogue's `dokument_typ` for each CTX document. That is 15 labels: enough to catch
  gross failures, too few for a rate.
- **Page level:** 300 pages stratified by those labels, with every page of the rare labels, annotated by AMČR or
  ARÚP/ARÚB with the written definitions. A double-annotated batch of 50 measures agreement.
- Model output is never used as gold.

**Runs:**
- **Inputs:** images only. There is no text arm: a type is form, and form is read from the image.
- **Models:** Clef, then Clef-Flash; Strands only if its vision extra answers (#58 Phase A).
- **Structure:** flat against two-level; at document level, `--doc-pages` 1 (the title page) against 4.

**Metrics:**
- accuracy and macro-F1 per level, and the confusion matrix by group;
- Brier and ECE, and coverage against error for the `review` lane;
- the agreement of the page's group with page-classification's label (e.g. `photograph` on a `PHOTO` page), as a
  cross-check between the two image tools, never as an input;
- latency per page and per document (early image requests were slow);
- `invalid` answers and timeouts.

**Fixtures:**
- `tools/stage_stub.py` answers `/v1/systemone` with fixed probabilities.
- `tests/fixtures/digital/` PDFs (`image_only.pdf`, `table.pdf`, `two_column.pdf`, …) drive `tests/test_describe.py`
  over real HTTP, as for the other stages.
