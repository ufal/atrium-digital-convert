# [\#9 Issue](https://github.com/ufal/atrium-digital-convert/issues/9) `open`: Develop processing of any possible inputs - CSV, IMG, PDF, DOCX, etc
**Labels**: `enhancement`, `development`, `integration`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-11-12 18:04](https://github.com/ufal/atrium-digital-convert/issues/9):

Two types of input are incoming: 
- text only, visual aspect is absent - TXT, CSV, TSV, JSON, etc
- visually rich and containing textual content - PDF, DOCX, maybe image formats for separate pages, etc

The repo should be able to process every possible input option to describe its contents or extract them and pass them further. Visual cues get textual representation in the resulting files, while the textual information should be extracted and recorded as is for future use. 

Visual features will be propagated to ATR and the page classifier repo. So the digital-convert repo should select the pages of the input document to be processed by the visually-based workflows. So far,  this repo should just record information for further pipeline steps.

Textual content goes to OCR post-processing to measure the quality of the extracted text. The decision on whether the extracted text is decent or garbage is not made in the first processing pass of the digital-convert repository.

DOCX files are rendered and passed on as images and text at the same time. 



#### <img src="https://avatars.githubusercontent.com/u/20186892?u=81493d22a8cb5fce679ac0e5e32fd98a04d777c6&v=4" width="50">[motyc](https://github.com/motyc) commented at [2026-11-12 22:59](https://github.com/ufal/atrium-digital-convert/issues/9#issuecomment-6838301982):

Thanks, this matches most of how we have planned the AMČR route ([ARUP-CAS/aiscr-docs-pipeline#12](https://github.com/ARUP-CAS/aiscr-docs-pipeline/issues/12)). A few points to check that we mean the same thing:

1. **Text quality is not judged in digital-convert.** Agreed. ocr-postprocess scores every line from every source, born-digital included, and is the only place that decides whether text is decent. Gibberish found there is flagged by its category; it does not send the page to OCR. digital-convert's per-line `Garbage` / `Inverted` verdict would become a flag that scoring may read, not a `categ` value.
2. **One page check does stay in the first pass.** A page whose text layer does not decode at all (fonts or glyphs without a Unicode mapping), a page whose text layer is an earlier OCR run, and a page with no text go to ATR, because the rendered page shows text the layer does not hold. We decide this before ATR runs: the whole document then goes through ATR once, with those pages forced, and there is no second routing step afterwards. So this is the selection of pages for the visual workflows that your issue describes, not a judgement of text quality.
3. **`garbled` should be narrowed to that.** The README defines `garbled` as broken font encodings, glyphs without a Unicode mapping, *and words losing letters*. The first two are decode failures and fit point 2. Words losing letters is a quality question, so we would leave it to scoring (point 1) rather than to the page verdict. Does that work for you?
4. **Text-only inputs (TXT, CSV, TSV, JSON).** Fine with us. They have no pages to render, so they skip the visual workflows and go straight to scoring.
5. **DOCX rendered and passed on as images and text.** Agreed on rendering: it gives office files the page geometry they lack today, in the same `pt` coordinates as PDF. Passing the pages on to the visual workflows should follow the same rule as a born-digital PDF, though: only the pages from point 2 go to page-classification and ATR. We considered also sending every page that carries an embedded image, and decided against it: in our documents the embedded images are mostly photos, with no text to read, so a DOCX page with good text would go through ATR for nothing.

Done on `test`:

- [#10](https://github.com/ufal/atrium-digital-convert/pull/10), points 1–3: decode verdicts are line flags, words that lose letters are left to scoring, and `garbled` means a layer that does not decode.

Office documents keep their own text, placed on the pages of a LibreOffice rendering; only a page whose rendering shows text the document lacks goes to the ATR, with the rendered PDF handed over.
- [#12](https://github.com/ufal/atrium-digital-convert/pull/12): a page whose rendering shows nothing at all is routed `empty`, so a blank page no longer sends the whole document to the ATR; any mark still does (point 2). Boxes are on the displayed page, as the ATR measures them.

Images still go straight to the ATR.

UPD

Inputs on `test` now (status described briefly):

- Read: PDF; DOCX, DOC, ODT, RTF (rendered); XLSX, XLS, ODS, TXT, CSV, TSV, JSON (as is). Anything else gets 415, PPTX and ODP included.
- A document with ATR pages ends in one record: ocr-postprocess merges the ATR's docproc with ours and keeps the text layer on the other pages ([ufal/atrium-ocr-postprocess#13](https://github.com/ufal/atrium-ocr-postprocess/pull/13)).
- The hub's digital E2E runs PDF, DOCX (a mixed one included), CSV and TXT through the `:test` images, from the command line and through both services ([run](https://github.com/ufal/atrium-project/actions/runs/43842746989)).

Plus, nuances/TODOs:

- Gaps: spreadsheets keep text cells only (numbers and dates are dropped; a CSV keeps every cell), RTF tracked changes are not accepted, and page breaks follow LibreOffice rather than Word.
