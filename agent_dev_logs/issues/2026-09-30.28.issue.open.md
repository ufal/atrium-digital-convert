# [\#28 Issue](https://github.com/ufal/atrium-llm-enrich/issues/28) `open`: Born-digital production path and `api-digital`
**Labels**: `development`, `integration`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-09-30 07:21](https://github.com/ufal/atrium-llm-enrich/issues/28):

Promote the existing born-digital converter from a command-line capability into the production service path required for S3.

Scope:
- introduce `api-digital` as an independent production service;
- apply the common ATRIUM health, `/info`, typed request/response and stable error contracts;
- support the AMČR-supported born-digital formats: PDF, DOCX, ODT, RTF, XLSX and ODS;
- use LibreOffice for the agreed DOC/XLS conversion path;
- establish the shared document reader and text-layer check used by the born-digital and OCR paths;
- identify pages without a usable text layer and hand them to OCR;
- feed born-digital lines into the same downstream quality/NLP record path as OCR-derived text;
- construct TEITOK from record line positions when ALTO is unavailable.

Acceptance criteria:
- born-digital documents can enter the same `atrium_document` processing chain as scanned documents;
- unsupported or unusable text layers receive an explicit registered reason rather than silently passing through;
- OCR-required pages are handed off to the ATR/OCR route;
- downstream line quality and NLP processing operate on the resulting shared record;
- `api-digital` is deployable using the same operational conventions as the other production services.
