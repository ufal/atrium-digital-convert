#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-09-30 07:21](https://github.com/ufal/atrium-digital-convert/issues/2):

Promote the existing born-digital converter from a command-line capability into the production service path required for S3.

Scope:
- introduce `api-digital` as an independent production service;
- apply the common ATRIUM health, `/info`, typed request/response and stable error contracts;
- support the AMČR-supported born-digital formats: PDF, DOCX, ODT, RTF, XLSX and ODS;
- use LibreOffice for the agreed DOC/XLS conversion path;
- establish the shared document reader and text-layer check used by the born-digital and OCR paths;
- identify pages without a usable text layer and hand them to OCR;
- feed born-digital lines into the same downstream quality/NLP record path as OCR-derived text;
- construct TEITOK from record line positions when ALTO is unavailable.

Acceptance criteria:
- born-digital documents can enter the same `atrium_document` processing chain as scanned documents;
- unsupported or unusable text layers receive an explicit registered reason rather than silently passing through;
- OCR-required pages are handed off to the ATR/OCR route;
- downstream line quality and NLP processing operate on the resulting shared record;
- `api-digital` is deployable using the same operational conventions as the other production services.

Thanks, @motyc. We are now treating #2 as the production born-digital originator/API rather than only a converter task.

The planned direction is:
- production endpoint **`POST /reformat`**;
- dedicated **`api-digital`** service/image, separate from the former LLM API;
- AMČR seed support, including preservation of `doc_id` and validation of `source.sha512` with **`source_digest_mismatch`** on mismatch;
- support for the agreed born-digital formats, with DOC/XLS going through the LibreOffice path;
- explicit `ocr_text_layer` refusal and page-level `needs_ocr` for documents containing material that must go through OCR;
- OCR pages merged back into the **same document identity**, not treated as a separate document;
- final line-quality scoring owned by the common `ocr-postprocess` path, so born-digital and OCR text use the same quality semantics;
- downstream TEITOK generated from record geometry when ALTO is not available.

The immediate target is a working API draft in ~2 weeks and a production-runnable service by the end of October. We will also freeze the OpenAPI/service contract and validate the full seeded path through the current six production stages before calling the service production-ready.

For the AMČR side, the main contract points that should remain stable are therefore `/reformat`, seed/source identity preservation, `source_digest_mismatch`, explicit OCR-required page handling, and keeping the resulting record compatible with the same downstream pipeline as OCR-originated documents.

#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) commented at [2026-10-05 06:09](https://github.com/ufal/atrium-digital-convert/issues/2#issuecomment-5989067703):

@motyc thank you. Here are the answers to your three questions, and what lands in **`v1.1.0-beta`**. The implementation is on `test` in 20dabd8, and the shared record module it relies on in b1cbb0c. The tag follows by 16 October.

**1. Identity — confirmed as you proposed.**
- The repository and service id are `atrium-digital-convert`. The spec declares the rename (`x-atrium-service-previous: atrium-llm-enrich`).
- The images are `ghcr.io/ufal/atrium-digital-convert-api` (the production service) and `ghcr.io/ufal/atrium-digital-convert-digital` (the command line). There is one spec, `service/openapi.json`, attached to every release.
- The program id inside the record stays `digital-convert`.

**2. `ocr_text_layer` — both readings, decided by one declared setting, `OCR_LAYER_DOCUMENT_SHARE` (default `0.5`, reported in `/info`).**
- If prior-OCR pages make up at least that share of a PDF's text-bearing pages, the whole document is refused: `422`, `reason: "ocr_text_layer"`. Route the document to OCR as a scan.
- Below that share you get a record. The prior-OCR pages carry `pages[].needs_ocr: true` with a reason that names the prior OCR layer.
- Pages without a usable text layer get the same flag: no text layer at all, or a layer that does not decode (broken font encodings).

**3. The merge — yes, as you describe it.**
- Temporal sends the `needs_ocr` pages through the OCR route, and ocr-postprocess merges their ATR ALTO into the same record (same `doc_id`; W4).
- The shared record module already authorises exactly that hand-off: the converter's own `needs_ocr` is the permission.
- `POST /reformat` makes no call to any other service.
- W4 itself is ocr-postprocess's next step and is not part of this release.

**`paradata`.** Every `/reformat` response carries `paradata`: the run's RO-Crate `CreateAction`, program `digital-convert`. Its `run_uuid` is stamped into every block the run wrote, as in the frozen contract (ufal/atrium-project#71).

**What `v1.1.0-beta` contains**

| | |
|---|---|
| `POST /reformat` | file (+ optional AMČR seed) → `document_json`; `markdown=true` adds the annotated Markdown; `paradata`. The endpoint for the AMČR route. |
| Seed handshake | the seed's `doc_id` is kept, and `source.sha512` is checked against the uploaded bytes **before anything is parsed** → `422 source_digest_mismatch`. |
| Formats | PDF, DOCX, ODT, ODS, XLSX, RTF, and DOC/XLS through headless LibreOffice (record says the original DOC/XLS; LibreOffice is not counted in the record's licence, as agreed on #4). Recognised by content, not by extension. |
| Refusals | `415 unsupported_media_type` (lists the accepted types), `422 ocr_text_layer`, `422 source_digest_mismatch`, `422 invalid_record`, `413/422 limit_exceeded` (`MAX_UPLOAD_MB` 50, `MAX_PAGES` 2000), `429 busy`; every error has the common `{status, reason, detail}` body. |
| Output licence | MIT (the light engine's libraries only). |
| `POST /describe` *(optional)* | see below. |

**New and optional: `POST /describe`.** This is not part of the AMČR route, and `/reformat` is unchanged by it. `/describe` does the same conversion, then adds a per-page assessment:
- whether the embedded text is usable (`text_layer`);
- if it is not, what kind of page it is (page-classification's category);
- whether the text reads (ocr-postprocess's line-quality model, a new `POST /score_record` = W3);
- where the page should go next (`nlp`, `ocr`, `htr` or `none`), with the reason;
- its layout counts and its text.

It calls those two services only when their URLs are configured. A stage that is not configured, or is down, is reported in the response, never a failed request. It is meant for triage, demos and the sandbox. If you want it in the pilot later, it needs page-classification `v1.9.2-beta` (ufal/atrium-page-classification@41c84ca) and ocr-postprocess `v1.9.0-beta` (ufal/atrium-ocr-postprocess@648aae7).
