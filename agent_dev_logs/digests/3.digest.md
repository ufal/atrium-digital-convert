## 🧭 Current ownership after the 2026-10-01 repository moves

This issue must no longer be described as an `llm-enrich`-owned format decision. The architecture has changed:

- **`ufal/atrium-digital-convert`** is now the **born-digital PDF/DOCX conversion owner**. Issue [#3](https://github.com/ufal/atrium-digital-convert/issues/3) owns the LLM-input format decision; [#4](https://github.com/ufal/atrium-digital-convert/issues/4) owns the PDF/DOCX handling and complex-layout/OCR hand-off work; [#2](https://github.com/ufal/atrium-digital-convert/issues/2) owns the production `/reformat` service.
- **`ufal/atrium-page-classification`** remains the **page-treatment router**. Its PDF service classifies every page; it can inform whether a page should follow deterministic extraction, OCR, or a more layout-aware route. It does **not** define a second LLM input format.
- **`ufal/atrium-ocr-postprocess`** is the **OCR-side reader/scoring/merge owner** after the former `alto-postprocess` rename. It now owns the shared readers and the line-quality machinery used by the OCR path. Born-digital `digital-convert` vendors the common reader layer rather than inventing another parser stack.
- **`ufal/atrium-nlp-enrich`** is the **LINDAT NLP / TEITOK owner**. Its LLM and keyword stages have left the repository; it no longer owns the LLM engine or vocabulary implementation. TEITOK remains the structured, spatially faithful NLP representation and an upstream source for the canonical Markdown view.
- **`ufal/atrium-keyword-extract`** is now the **LLM/vocabulary successor**: it consumes the ATRIUM document record after `nlp-enrich` and owns the future controlled-vocabulary LLM stage plus the statistical keyword stage. In the current `v1.0.0-beta`, statistical extraction is implemented and controlled extraction is not yet wired; that stage must consume the same canonical document representation rather than creating a competing Markdown dialect.
- **`ufal/atrium-translator`** is a downstream record-preserving consumer. It accepts/returns `document_json`, but it is not an owner of the LLM input-format decision.
- **`ufal/atrium-project`** owns the frozen **`doc-schema-v1`** contract and the hub-level DU benchmark/evaluation work. Issue [#22](https://github.com/ufal/atrium-project/issues/22) is currently deferred until after the pilot and remains the place for the broader empirical comparison/gold set.

The old `atrium-llm-enrich#11` wording about “the LLM engine leaving this repository” is therefore historical. The current destination is `atrium-keyword-extract`, and the format owner is `atrium-digital-convert`.

## 🎯 Goal

Decide which representation should actually reach the LLM for document understanding and downstream LLM tasks, while preserving enough document structure and spatial provenance for page-level grounding, without coupling the system to one vendor parser.

The issue began with this format/detail matrix:

| Format        | Detail level                                                                               |
|---------------|--------------------------------------------------------------------------------------------|
| PDF           | Max visual and textual                                                                     |
| InDesign XML  | Font types, letter spacing, graphics regions, complex layout and tables, etc.              |
| HTML+CSS      | Graphics + formatted text + complex layouts of tables and pages                            |
| DOCX          | Same as above                                                                              |
| Page/ALTO XML | Text regions and word-level positioning + graphics regions + hyphenation/table/layout data |
| MD            | Tables + formatted text, headers, lists, and compact structure                             |
| TXT           | Plain ordered text                                                                         |

The current answer is not “pick one source file format”. It is a **layered representation decision**:

1. **Original/source inputs remain whatever the archive supplies** (PDF, DOCX, etc.).
2. **`atrium_document` JSON is the canonical pipeline record** and the regeneration point for document-level views.
3. **TEITOK/PAGE/ALTO remain the spatially precise representation** for OCR/layout provenance and line-level alignment.
4. **Annotated Markdown is the canonical LLM diet** for document-level LLM ingestion where page-by-page image input is not itself the task.
5. **HTML is only an intermediate/structural transport or rendering aid, not the LLM diet.**
6. **TXT is a degraded fallback**, not the preferred semantic representation.

## 🧭 The format decision

### Annotated Markdown is the LLM diet

The Markdown is not “plain Markdown produced by an off-the-shelf converter”. It is the **house annotated representation** whose structural syntax is Markdown and whose machine-readable geometry is carried by HTML comments/cues.

The current renderer stack is:

- `api_util/json_to_md.py` — canonical **AtriumDocument JSON → annotated Markdown** renderer;
- `api_util/xml_to_md.py --format layout` — canonical **TEITOK/ALTO → the same Markdown cue vocabulary**;
- `api_util/layout_md.py` — single cue vocabulary and detail profiles;
- `api_util/digital_to_json.py` — canonical PDF/DOCX-side record creation before Markdown rendering.

The Markdown therefore carries the semantic structure that an LLM should see — headings, paragraphs, lists, tables, footnotes — while retaining page and geometry cues that would otherwise be lost.

### Why not HTML+CSS?

HTML remains useful as an intermediate and as a structural representation for some extraction tools, but the project does not want raw HTML/CSS as its model-facing format. The original issue thread identified the token overhead of repetitive tags/styles and the poor fit with a compact document-level prompt. The current architecture keeps HTML available to parsers/adapters without making it the LLM contract.

### Why not raw PAGE/ALTO/TEITOK as the diet?

Those formats remain the spatial source of truth because they preserve positions and OCR alignment much better than Markdown. They are nevertheless verbose and expose implementation-level details that are not needed on every document-level LLM call. They therefore feed the renderer rather than replacing Markdown as the general-purpose LLM input.

### Why not TXT?

TXT remains the fallback for inputs where structure cannot be reconstructed, but it loses the hierarchy, tables, grouping, and page cues that the project explicitly wants to preserve.

### What about DOCX/PDF?

They are **inputs**, not the final LLM representation. The born-digital converter extracts them into the canonical record. This separation means parser libraries can change independently of the LLM-facing contract.

## 🧩 Visual cue contract

The issue originally proposed bare page markers such as `<!-- Page 14 -->`. The implementation has evolved into a richer, stable cue vocabulary in `layout_md.py`, including, where available:

- page boundaries and page labels;
- document/page dimensions;
- bounding boxes;
- margins/canvas information;
- heading/style cues;
- page-header and page-footer regions;
- footnotes;
- table structure;
- OCR / `NEEDS_OCR` state and reason codes.

The exact cue set is profile-dependent. `full` is the current default; `standard` and `minimal` reduce cue volume while preserving the same text. The hub benchmark has already measured substantial character/token savings for lighter profiles; the quality comparison is intentionally postponed until there is a gold set.

The core invariant is **one text/layout dialect**: JSON and TEITOK sources must render through the same cue vocabulary rather than producing subtly incompatible prompts.

## 📦 Canonical record and what Markdown deliberately excludes

`api_util/json_to_md.py` explicitly reads `pages`, `lines`, `tables`, and `content` plus their layout metadata. It intentionally does **not** read the record's `enrichment` block.

That exclusion is load-bearing: the `enrichment` block contains outputs generated by the LLM/keyword stage itself. Re-rendering a record with those fields as input would feed the model its own earlier answer on a later run. Therefore the Markdown view must remain grounded in the source/document plane, not in prior model output.

The same point changes the old 2026-08-02 stress-test acceptance criterion. It is **not correct to require “no entities, keywords or enrichment lost in the Markdown”**. Those data belong in the JSON record. The Markdown stress suite should instead verify:

- page count/order;
- source text and line order;
- grouping/paragraph boundaries;
- tables and their anchors;
- page labels and bboxes;
- all emitted layout/OCR cues;
- stable rendering of edge cases.

Entities/keywords must be validated in the JSON/TEITOK contracts, not expected to appear in the Markdown prompt.

## 🔀 Role of page-classification and OCR quality

The original issue suggested using `atrium-page-classification` to “separate MD and HTML+CSS”. That is no longer the architecture.

`atrium-page-classification` classifies the **page and treatment need**. It can steer extraction vs OCR vs a more layout-aware parser, but all successful branches converge on the same `atrium_document`/annotated-Markdown contract.

Likewise, `atrium-ocr-postprocess` now owns the shared reader and line-quality machinery. Its categories and `quality_score` are significant upstream signals because `json_to_md.py` can exclude lines already marked as untrustworthy (including OCR `Trash`) before an LLM sees them. The document record therefore carries the quality decision into the rendering step without making the LLM parser itself responsible for OCR cleanup.

The born-digital path also rejects PDFs carrying a prior OCR text layer using the stable `ocr_text_layer` reason code and hands those documents toward the OCR path. That distinction is important: a document that *looks* like a text PDF is not necessarily suitable for the born-digital text extractor.

## 🧪 Benchmark grounding

The earlier research used OmniDocBench, PubTabNet/FinTabNet, DocVQA-family resources, KIE benchmarks, PAGE/ALTO OCR datasets, and Grobid as reference points. Those remain useful as **background evidence**, but the current hub plan is deliberately more in-domain:

- the broader DU experiment lives in [ufal/atrium-project#22](https://github.com/ufal/atrium-project/issues/22);
- that benchmark is currently **deferred until after the AMČR pilot** because its in-domain gold set is not yet available;
- the complex-layout Docling/MinerU comparison now belongs to [digital-convert#4](https://github.com/ufal/atrium-digital-convert/issues/4), not to a separate generic LLM benchmark;
- the token/cue-detail comparison belongs to the hub benchmark once it resumes;
- OCR engine competition is not part of this issue anymore and is handled on the AMČR side/back-up evaluation.

The code-side benchmark primitives (`eval_metrics.py`, `sample_stratify.py`, `bench_compare.py`) therefore remain relevant, but this issue no longer promises an immediate format bake-off. The next benchmark round should measure **quality + token cost + page-citation preservation** on the exact in-domain sample rather than infer a winner from generic benchmarks alone.

## 🛠️ Current implementation state

### Landed

- **Canonical JSON → annotated Markdown** exists in `digital-convert`.
- **Canonical TEITOK/ALTO → annotated Markdown** exists with the same cue vocabulary.
- **PDF/DOCX → AtriumDocument JSON** is the active born-digital route; the old direct Markdown converters remain only as deprecated compatibility paths.
- JSON rendering supports **`full` / `standard` / `minimal`** cue profiles; `full` remains the default.
- JSON rendering can filter **untrustworthy line categories** and carry page/OCR metadata into the prompt.
- PDF/DOCX parity work (G1–G8) has been landed and tested.
- The production service direction is now explicit: `digital-convert#2` will expose `/reformat`, with stable error codes and the `ocr_text_layer` contract.
- `ocr-postprocess` is the common reader/scoring owner for the OCR side.
- `nlp-enrich` and `translator` accept the shared `document_json` contract.
- `keyword-extract` is the current home for the LLM/vocabulary successor; its controlled mode is not yet live, so there is still time to make the renderer ownership/integration contract explicit before that mode is enabled.

### Still open

- a dedicated **Markdown stress suite** covering the full JSON and TEITOK feature surface has not yet replaced the case-by-case tests;
- complex two-column / difficult-layout pages still need empirical comparison (Docling/MinerU phase in #4);
- the OCR hand-off and born-digital/OCR reader parity continue under #4/#ocr-postprocess;
- the hub gold set for #22 does not yet exist, so the quality half of the detail/token bake-off is not done;
- the final end-to-end **LLM page-citation verifier** (`[Source: <doc_id>, Page N]` or equivalent) is still future work.
