## 🎯 Goal

Define a single, production-compatible way to ingest the three PDF situations named in the original issue — curve-only pages, scanned/image-only pages, and digital-born pages with text — together with DOCX, while preserving enough structure and geometry for downstream ATRIUM processing and optional LLM-friendly document rendering.

The current design is no longer “PDF/DOCX → Markdown and then LLM enrichment in this repository”. It is:

```text
PDF / DOCX / other born-digital input
        │
        ▼
  digital-convert
        │
        ├── `atrium_document` record  ← canonical production output
        │      pages / lines / bboxes / tables / source / `needs_ocr`
        │
        └── optional `json_to_md` rendering
                 │
                 └── annotated Markdown for document-level consumers

`needs_ocr` pages ──route/orchestration──> AMČR OCR
                                         │
                                         ▼
                              ocr-postprocess merges OCR pages
                                         │
                                         ▼
                           nlp-enrich → keyword-extract → translator
```

The converter itself is therefore an **originator of the positional document plane**, not an LLM service and not an orchestrator of the other stages.

## 🔎 What the research established

### 1. PDF classes collapse to two processing paths

The original three-way taxonomy is operationally two paths:

| PDF situation            | Detection / treatment                                           | Production interpretation                                            |
|:-------------------------|:----------------------------------------------------------------|:---------------------------------------------------------------------|
| Digital-born             | Extractable text plus usable font/character evidence            | Read directly into the `atrium_document` record.                     |
| Curve-only               | No trustworthy character extraction because glyphs are outlines | Do not fabricate text; route for OCR.                                |
| Scanned/image-only       | Text layer absent or unusable                                   | Route for OCR.                                                       |
| Digital-born but garbled | Characters exist but decode sanity fails                        | Treat affected pages as `needs_ocr`; do not trust the embedded text. |

A real document can contain several classes at once, so the decision is page-aware rather than a single document-wide “PDF type” switch.

The research also established that Czech text can extract as systematically corrupted Unicode when `/ToUnicode` information is missing. That is why the route cannot equate “some text was extracted” with “text is trustworthy”.

### 2. Canonical production output is `atrium_document` JSON

The September implementation round resolved the previous ambiguity between “document understanding output” and “LLM input”. The canonical converter result is the shared record with, at minimum:

- source identity/provenance;
- pages and canvas information;
- lines and their positional geometry;
- blocks/groups/regions;
- tables and other structured document elements;
- text-layer checks and `needs_ocr` metadata.

This record is what the rest of ATRIUM should consume. It also lets the service preserve an AMČR-seeded `doc_id` and `source.sha512` instead of inventing a second document identity.

### 3. Annotated Markdown is a derived representation, not the system-of-record

The former #10 design remains useful, but it has moved one layer down:

```text
source → digital-convert → atrium_document → json_to_md → optional LLM/document consumer
```

The annotated Markdown uses ordinary Markdown plus HTML comments for high-value layout cues, such as:

- page breaks / page metadata;
- block bounding boxes;
- font/style and alignment cues where they survive extraction;
- column and indentation information;
- headers/footers and footnotes;
- tables and figure/image placeholders;
- OCR provenance cues.

It is intended to be LLM-friendly and human-readable, but it is **not** a second authoritative record. The record remains the source of truth for page/line geometry and provenance.

### 4. DOCX/HTML intermediates are no longer the default PDF strategy

The original issue asked whether DOCX or HTML should be used as an intermediate for PDF processing. The measured and implemented route no longer needs that indirection for the baseline case:

```text
PDF/DOCX → digital IR → atrium_document JSON → annotated Markdown on demand
```

`python-docx` remains the light DOCX reader. HTML can still be useful as a local/intermediate representation in a specialized adapter, but it is not the canonical output contract and should not be inserted into the production pipeline merely to satisfy the old issue wording.

### 5. Complex layout remains a separate evaluation phase

The light PDF route is intentionally permissive and CPU-oriented. Real two-column/complex-layout pages can still defeat a purely geometric light reader. The `test` branch contains an opt-in Docling adapter over the common digital IR; its live model quality was not the production decision.

Project [#22](https://github.com/ufal/atrium-project/issues/22) remains the evaluation track for document-understanding tools. Docling/MinerU are therefore candidates for the later complex-layout phase, not a baseline dependency of the production digital image.

## 🔐 Stable contract decisions

### `ocr_text_layer`

The previous-OCR text-layer refusal is now an explicit cross-repository contract. When the service is delivered, a document rejected for this reason returns HTTP 422 with exactly the registered reason code `ocr_text_layer`. The common reason registry and the public service specs are intended to keep this name stable; the route step may use it to send the original document to the OCR connector.

The current converter also has a mixed-PDF nuance: the implementation can keep a minority of prior-OCR pages in the born-digital record and mark them for OCR, while refusing the document when the affected share reaches the current threshold. The **production AMČR rule for mixed PDFs still belongs to #2's API-contract discussion and should not be re-described here as finally frozen merely because a constant exists in the CLI**.

### `source_digest_mismatch`

AMČR explicitly accepted the additional seed check in #2: the uploaded bytes must match `source.sha512`; a mismatch returns the registered 422 reason `source_digest_mismatch` and must not create a misleading output record. This is an #2 implementation item, not a new design branch in #4.

### `/reformat` and service identity

The current production endpoint is **`POST /reformat`**. The program id remains `digital-convert` in the record. The production service identity should follow the repository identity (`atrium-digital-convert`) and its API image should use the same repository name; the earlier historical bootstrap spelling `atrium-digital-born-convertor` is obsolete and must not survive into the final contract.

### No service-to-service calls inside the converter

`digital-convert` should not directly invoke page-classification, OCR post-processing, NLP, keyword extraction or translation. Temporal / the AMČR route coordinates those stages. The converter exposes enough record metadata and reason codes for the orchestrator to make the next decision.

## ✅ What's settled for #4

- PDF curve-only and scanned pages belong to the OCR route rather than to a second PDF-to-text library stack inside digital-convert.
- Digital-born PDF/DOCX conversion is based on the shared `atrium_document` record, not on direct LLM prompting.
- `digital_to_json` → `json_to_md` is the default internal route for derived annotated Markdown.
- The old direct PDF/DOCX Markdown converters are deprecated rather than immediately deleted.
- Markdown is an optional, derived representation; the record is canonical.
- Page/line geometry must survive into the record wherever the source permits it.
- Page-level `needs_ocr` is the normal hand-off signal for unusable pages.
- A prior OCR text layer is an explicit refusal case with the stable 422 reason `ocr_text_layer`.
- OCR itself is outside the converter; the AMČR route supplies OCR output and `ocr-postprocess` merges it.
- One shared line-quality semantics is required; `ocr-postprocess` owns it.
- TEITOK for born-digital input is produced downstream from record geometry by `nlp-enrich`.
- DOC and XLS use headless LibreOffice in the production digital image, declared conditionally as an MPL-2.0 component.
- Complex-layout parsing remains a later benchmark/evaluation phase, tied to project #22.
- flexiconv remains a GPL-3.0-or-later CLI option outside the production service image and outside the AMČR production chain.
- The production service work is #2; #4 should not duplicate that implementation tracker.
