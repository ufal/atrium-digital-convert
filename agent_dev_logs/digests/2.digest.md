**Labels**: `documentation`, `a big one`, `development`, `integration`

**Status**: 🟡 **Partially implemented.** The born-digital converter itself is now a substantial, tested `digital-convert` CLI: PDF and DOCX produce the current `atrium_document` record, page-level `needs_ocr` is implemented, the prior-OCR text-layer refusal is registered, and the hub already has a dedicated born-digital smoke workflow. The missing production piece is still the HTTP service: `service/api.py` on `test` is the inherited LLM keyword API (`SERVICE = "atrium-llm-enrich"`), while the Docker `api` target is still built from the old remote/LLM service. The repository split also changed the downstream contract: `ocr-postprocess` now owns the common text readers and quality semantics, `nlp-enrich` is the LINDAT/TEITOK stage only, `keyword-extract` owns both keyword kinds, and the six-stage hub map treats `digital-convert` as the born-digital originator rather than an LLM stage.

## 🎯 Goal

Promote the existing born-digital converter from a command-line capability to the production service that the AMČR route calls for born-digital input, while keeping the current `atrium_document` identity/origin rules and making its output usable by the same downstream record pipeline as OCR-originated documents.

The issue's scope, in the current architecture, is:

1. a dedicated `api-digital` HTTP service with the common ATRIUM health, `/info`, limits, typed response and stable error contracts;
2. the production endpoint **`POST /reformat`**;
3. AMČR seed support, including preservation of `doc_id`, `source.sha512`, file name and media type;
4. a registered **`source_digest_mismatch`** refusal when the seed digest does not match the uploaded bytes;
5. PDF, DOCX, ODT, RTF, XLSX and ODS, with the agreed LibreOffice path for legacy DOC/XLS inputs;
6. the shared text-bearing reader contract used by the born-digital and OCR paths, without making the two originators co-own the same positional plane;
7. page-level `needs_ocr` for born-digital pages whose embedded text exists but is not trustworthy, plus the existing document-level `ocr_text_layer` refusal for a PDF dominated by an earlier OCR layer;
8. OCR re-processing of only the flagged pages, merged back into the **same document identity** without changing `source.origin`;
9. common line-quality semantics owned by `ocr-postprocess`, with digital-convert remaining the owner of born-digital text/geometry fields;
10. TEITOK generation from `pages[].canvas` and `lines[].bbox` when no ALTO exists, owned by `nlp-enrich` as the downstream consumer rather than by the converter itself;
11. a seeded hub E2E that proves the route instead of only proving the standalone CLI.

The issue is therefore no longer an isolated converter task. It is the **born-digital originator/API contract at the entrance to the current six-stage ATRIUM architecture**.

Two old assumptions from the pre-split #28 plan must therefore be removed from this issue's documentation:

- `llm-enrich` is **not** the production owner of `api-digital`; `atrium-digital-convert` is.
- keyword extraction is **not** part of `digital-convert` or `nlp-enrich`; it is the separate `keyword-extract` stage.

The historical `alto-postprocess` name remains relevant only through the successor mapping to `ocr-postprocess`; the current production repository is [`atrium-ocr-postprocess`](https://github.com/ufal/atrium-ocr-postprocess/tree/test).

## 🧵 Decision trail

- **2026-09-26, AMČR discussion / #10:** the born-digital path is a production service; all supported input types use one reader family, the route can hand OCR-required pages to OCR, line quality is one common semantics, and TEITOK can be built from the record when ALTO is absent.
- **2026-09-27, #67:** `api-digital` and the registered 422 `ocr_text_layer` refusal were placed in the pilot order.
- **2026-09-28, #32 round 2:** `ocr_text_layer` became a registered ATRIUM refusal code and is pinned by a contract test in the converter.
- **2026-09-30, AMČR meeting:** the endpoint was settled as **`/reformat`**; the repository became the born-digital converter; the program id remains `digital-convert`.
- **2026-09-30, issue #2:** AMČR confirmed that a seed with the wrong `source.sha512` must be refused with **`source_digest_mismatch`**. This code is agreed but is not yet implemented/registered in the current tree.
- **2026-09-30, issue #2:** AMČR asked for `api-digital` in the S2 pilot around the end of 2026 and asked for a proposed date by the 11 November meeting. ÚFAL answered with a working draft in about two weeks and a production-runnable service by the end of October.
- **2026-10-01, repository split:** `atrium-alto-postprocess` became `atrium-ocr-postprocess`; keyword extraction moved to `atrium-keyword-extract`; `atrium-nlp-enrich` dropped its keyword/LLM responsibilities; the former born-digital work was moved into `atrium-digital-convert`.
- **2026-10-01, record-contract round:** `digital-convert` is an accepted originator of the positional plane for `digital-born-*` records; `ocr-postprocess` is the successor originator for OCR records and can re-originate flagged pages in a digital-born record when `needs_ocr` authorises the hand-off.
- **2026-10-02, latest issue thread:** the open identity question is now whether the first HTTP service should publish as `atrium-digital-convert` (matching the repository) and use `ghcr.io/ufal/atrium-digital-convert-*`, rather than the earlier historical bootstrap name `atrium-digital-born-convertor`. The question should be closed before the first API release because GHCR package names are not renamed later.

## ✅ What's settled

- The production endpoint is **`POST /reformat`**.
- `atrium-digital-convert` is the repository and **`digital-convert`** is the record program id; existing record ownership and source-origin rules should not be renamed again.
- `digital-convert` is the **originator** of the born-digital `pages` / `content` / `lines` / `tables` plane. `ocr-postprocess` remains the OCR originator and may take over only the pages explicitly authorised by `needs_ocr`.
- `digital-convert` does **not** synchronously call page-classification or ocr-postprocess as internal dependencies. The route/orchestration layer decides which stage to invoke and which page subset to send to OCR.
- `page-classification` remains a scan/image stage; it is not required for a clean born-digital document.
- `ocr-postprocess` is the current owner of the common text-bearing reader family and of the line-quality categorisation semantics.
- `ocr_text_layer` is a stable 422 refusal for a PDF that the converter decides is not genuinely born-digital because the invisible layer is an earlier OCR run.
- A digital-born page whose embedded text exists but does not decode safely is represented by `needs_ocr=true` plus `needs_ocr_reason`; routing policy remains outside the converter.
- AMČR explicitly accepted **`source_digest_mismatch`** for a seed/file mismatch.
- The service must return the current record contract and a `CreateAction` `paradata` object like the other production APIs.
- The keyword/LLM responsibilities are outside this issue after the repository split; `keyword-extract` is the downstream keyword stage.
- Complex Docling/MinerU processing is optional research/deferred work; it is not part of the minimal production `api-digital` service.

## ⏳ Open

1. **First-release service identity.** The historical plan used `atrium-digital-born-convertor` + `openapi-digital.json`. The latest issue comment proposes `atrium-digital-convert` and `ghcr.io/ufal/atrium-digital-convert-*`, matching the repository. This must be confirmed before the first API release.
2. **`source_digest_mismatch` registration and implementation.** Add the code to the shared reason registry/spec and pin it with an API contract test; compare the seed's `source.sha512` with the exact bytes received before doing any conversion.
3. **Mixed-PDF policy.** Confirm whether the existing 50% threshold is the intended AMČR rule. The implementation already provides a useful split: below the threshold, OCR-layer pages become `needs_ocr`; at/above it, the document is refused as `ocr_text_layer`.
4. **API surface.** Replace the inherited LLM app with `/reformat`, common `/health`, `/ready`, `/info`, limits, typed output and the registered error envelope. Decide once whether the public spec is `service/openapi.json` or the earlier planned `service/openapi-digital.json`; do not ship both as competing production baselines.
5. **Input set.** Wire ODT/RTF/XLSX/ODS through the common reader, and DOC/XLS through LibreOffice, without losing the original source identity or changing the `digital-convert` source-origin contract.
6. **OCR subset merge.** Define the route-level payload and merge key (`page_index` plus page label), then make the OCR connector return ALTO only for flagged pages. `ocr-postprocess` must merge those pages into the original record while preserving `source.origin = digital-born-*` and `doc_id`.
7. **Common quality.** Make the `ocr-postprocess` scorer write only its authorised quality fields on born-digital lines; `digital-convert` remains the writer of born-digital text/bbox/group/table structure.
8. **TEITOK from record geometry.** Give `nlp-enrich` a supported path that can consume the born-digital record's lines and native page/line geometry without requiring an ALTO file that does not exist.
9. **Production E2E.** Extend the hub born-digital smoke from the CLI image to the HTTP service and add the seeded route proof, including clean PDF/DOCX, mixed `needs_ocr`, whole-document `ocr_text_layer`, downstream quality/NLP and final record preservation.
10. **Production image/release cleanup.** Remove the inherited LLM API from the production target; align service id, `CITATION`, README, Pages, GHCR names, Docker metadata, API specs and hub maps; keep the research/legacy history out of the production image.
11. **Schedule.** A working API draft is due roughly **2026-10-16** and a production-runnable service by **2026-10-31**, matching the latest issue-thread commitments. The S2 pilot target is around the end of 2026; a concrete pilot/pinning date should be proposed before the **2026-11-11** AMČR meeting.
