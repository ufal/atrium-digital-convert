## 🎯 Goal

Promote the existing born-digital converter from a CLI capability into the **production originator service `api-digital`** used by the AMČR route.

The service must create the same `atrium_document` record consumed by the rest of the ATRIUM production chain and must participate in the same operational, contract, provenance and deployment conventions as the other production services.

The required service scope is:

1. independent production service `api-digital`;
2. common ATRIUM `/health`, `/ready`, `/info`, limits, typed request/response and stable error contracts;
3. `/reformat` as the settled endpoint name, replacing the earlier `/convert` design;
4. AMČR born-digital formats PDF, DOCX, ODT, RTF, XLSX and ODS, plus DOC/XLS through the agreed LibreOffice conversion path;
5. seed-aware processing preserving AMČR `doc_id`, source identity, filename and media type;
6. `source.sha512` validation against the uploaded bytes;
7. explicit `ocr_text_layer` refusal for PDFs whose text layer is a prior OCR layer or otherwise unusable;
8. explicit identification of pages requiring OCR;
9. OCR hand-off and merge of OCR-generated pages back into the same document record;
10. downstream use of the same line-quality/NLP path as OCR-originated text;
11. TEITOK construction from `lines[].bbox` / `pages[].canvas` when ALTO is unavailable;
12. optional record-derived Markdown for consumers such as keyword extraction;
13. a production image, OpenAPI asset and CI probe following the same conventions as the other five services.

## 🧭 Current architectural position

The September repository changes reduced the production system to **six production stages**:

```text
page-classification
        │
        ▼
ocr-postprocess
        │
        ├──────────────────────────────┐
        │                              │
        │                         born-digital
        │                              │
        ▼                              ▼
nlp-enrich                    api-digital /reformat
        │                              │
        ▼                              ▼
keyword-extract                document record
        │                              │
        ▼                              ├── usable text pages ──► normal downstream path
translator                      │
                                └── needs_ocr pages ──► ATR/OCR
                                                │
                                                ▼
                                      ocr-postprocess merge/score
```

The seeded E2E proof currently being assembled by the hub is explicitly intended to exercise:

```text
api-digital
    → page-classification
    → ocr-postprocess
    → nlp-enrich
    → keyword-extract
    → translator
```

for born-digital inputs, while allowing pages that need OCR to be reacquired and merged without creating a second document identity.

This means #2 is no longer a converter-only task. It is the **born-digital originator contract at the front of the six-stage production system**.

## 📦 Input and record contract

The service should accept:

```text
multipart/form-data
  file            required
  document_json   optional AMČR seed
  render          optional, e.g. `md`
```

The uploaded bytes are authoritative for the actual source content.

When `document_json` is supplied:

* preserve the seeded `doc_id`;
* preserve the AMČR source filename and media type;
* compare `source.sha512` against the uploaded bytes;
* refuse a mismatch with `reason: source_digest_mismatch`;
* never silently replace a conflicting source identity.

The service is an **originator**, so `source.origin` is written by the document reader itself. Downstream services may enrich the same record but must not create a second source identity.

## 🚫 Refusal/error contract

The API should use the common ATRIUM error envelope.

Expected initial mapping:

| Condition                                 |    HTTP | Registered reason / contract                      |
| ----------------------------------------- | ------: | ------------------------------------------------- |
| unsupported media                         |     415 | `unsupported_media_type` with the converter cause |
| unusable/prior OCR text layer             |     422 | `ocr_text_layer`                                  |
| seeded digest differs from uploaded bytes |     422 | `source_digest_mismatch`                          |
| encrypted document                        |     422 | `encrypted`                                       |
| corrupt/unreadable document               |     422 | `corrupt`                                         |
| request/archive exceeds limit             |     413 | `limit_exceeded`                                  |
| malformed seed record                     |     422 | `invalid_record`                                  |
| service/backend failure                   | 500/503 | common ATRIUM operational error                   |

The API must never silently treat an unusable text layer as successful born-digital extraction.

## 📚 Reader ownership after the repository split

The new architecture makes `atrium-ocr-postprocess` the owner of the shared document reader.

The intended arrangement is:

```text
atrium-ocr-postprocess
    └── shared document readers
          ├── digital-convert
          └── other consumers as required

atrium-nlp-enrich
    └── TEITOK reader
          ├── digital-convert
          └── keyword-extract

digital-convert
    └── record → Markdown renderer
          └── keyword-extract
```

Consumers should vendor these shared modules with explicit source/revision pins and a `para-drift` / parity test. They should not silently fork independent readers.

## ⚠️ Quality-scoring boundary

The current converter contains a decode-sanity/page-quality mechanism. This is useful for detecting bad text layers and deciding whether a page requires OCR, but it must not become a second production quality model.

The settled architecture is:

```text
digital-convert
    → extraction diagnostics / needs_ocr
    → common record
    → OCR merge where required
    → ocr-postprocess
    → authoritative line categorisation + quality_score
```

The final quality fields on born-digital lines must use the same quality semantics as OCR-derived lines.

## 🔬 TEITOK and geometry

The born-digital converter must preserve enough spatial information for downstream TEITOK generation:

* page identity / page index;
* page canvas where available;
* line bounding boxes;
* ordering information;
* tables and other record-owned structures where supported.

When ALTO does not exist, `nlp-enrich` creates TEITOK from those record positions instead of falling back to text-only TEITOK.

## 🐳 Production image

The current repository deliberately keeps the light `digital` stage separate from the former `remote`/LLM targets. `api-digital` must follow that separation:

```text
base
  │
  └── digital
        │
        └── api-digital
```

The production API image must contain the converter and its required document readers, but no research-only LLM stack, remote-provider client or large model runtime.

The heavy Docling path remains optional and must not be part of the production `api-digital` image.

The intended final service identity is:

```text
service id:       atrium-digital-born-convertor
program id:       digital-convert
endpoint:         /reformat
spec asset:       openapi-digital.json
```

The repository/package rename is a separate migration step; the service identity should not change again when that rename happens.

## ✅ Done when

The issue is complete when:

* a seeded PDF, DOCX, ODT and XLSX can enter through `/reformat`;
* DOC/XLS are accepted through the agreed LibreOffice path;
* the returned record preserves the AMČR seed identity and validates the source digest;
* a prior/unusable PDF OCR layer returns `422` with `ocr_text_layer`;
* pages requiring OCR are explicitly represented and can be handed to the ATR/OCR path;
* OCR pages can be merged into the same document record without changing `doc_id` or `source.sha512`;
* the resulting record reaches the common page/quality/NLP/keyword/translation chain;
* born-digital lines receive the same authoritative quality model as OCR lines;
* `nlp-enrich` can build TEITOK from record geometry when ALTO is absent;
* `/health`, `/ready`, `/info`, limits, errors and `CreateAction` match the common ATRIUM service contract;
* `openapi-digital.json` is committed, tested and attached to the release;
* `api-digital` is built and probed in CI;
* the production image contains only the intended converter/runtime dependencies;
* the seeded born-digital E2E is green;
* the final service/repository identity is stable enough for S2 to pin an immutable production artifact.
